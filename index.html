PRINCIPLE 01

Theory pays rent.

You can't ship around CAP, isolation levels, or backpressure. The fundamentals show up in your incidents whether you read them or not.

PRINCIPLE 02

Patterns > tools.

Tools change every three years. The pattern beneath them — saga, outbox, circuit breaker — has been the same for thirty.

PRINCIPLE 03

Knowing when not to.

Senior engineers are valued for the architectures they refuse, not the ones they propose. Every page here ends with "avoid when".

PRINCIPLE 04

Boring code is real code.

Every concept ships with a 60-line implementation in Go, Python (FastAPI), and Java (Spring Boot). Run it. Break it. Ship it.

How to read this

The pillars are ordered into four tiers. Each tier builds on the last — you can jump around, but the cross-references assume you've seen the foundations. If you read one tier per month, you'll have a senior engineer's mental model in roughly a quarter. If you're cramming for an interview, read tier 1 cover-to-cover, skim tier 2, and pick from 3 and 4 based on the role.

Recommended reading

Four books that complete the picture

This site teaches the breadth. These books teach the depth. If you only read one, make it DDIA. If you're targeting payments or logistics roles, pair with the applied pages above.

Must read

Designing Data-Intensive Applications

Martin Kleppmann · The single most recommended book for system design interviews. Replication, partitioning, consistency, batch vs stream — the theory behind every page on this site.

Covers: pillars 01, 02, 05, 06
Deep dive

Database Internals

Alex Petrov · B-trees, LSM trees, WAL, MVCC, storage engine internals. When an interviewer asks "why Postgres over Cassandra," this book gives you the engine-level reasoning.

Covers: pillar 02 (deep)
Accessible

Understanding Distributed Systems

Roberto Vitillo · A more accessible entry point to distributed systems than DDIA. Consensus, failure detection, replication — great for reinforcing pillar 01 concepts before going deeper.

Covers: pillar 01 (reinforcement)
Thinking

A Philosophy of Software Design

John Ousterhout · Not about systems — about how you think about complexity, abstractions, and API surfaces. Deep modules, information hiding, tactical vs strategic programming. The senior mindset book.

Covers: code design, senior thinking
