Tier five · Pillar 08

Numbers the business can sign off on.

The ERP runs the business; the data platform explains it. Columnar files on object storage, table formats that add transactions, ingestion that survives retries, models with a declared grain, and reconciliation that proves the totals before anyone sees them. Tools change every couple of years; these first principles do not. Every example follows Northwind Cold Chain, a fictional group with an ERP and a WMS in each of four entities, four currencies and a month-end close that has to tie out.

PRINCIPLE 01

Separate the workloads.

Transactions want rows, keys and milliseconds; analytics wants columns, scans and history. Running both on one engine makes both worse.

PRINCIPLE 02

Layers are contracts.

Bronze, silver and gold are promises about what a consumer can rely on, not folders or products. Enforce them with grants and CI, not goodwill.

PRINCIPLE 03

Every load must be re-runnable.

Deterministic batches, keyed merges and partitions that replace themselves turn a 02:00 failure into a retry. Exactly-once is a property you build, not one you are given.

PRINCIPLE 04

Reconcile or it isn't true.

A dashboard that disagrees with the ledger is worse than no dashboard. Prove the totals against the source on every load, and publish only when they tie.

01

OLTP vs OLAP · why analytics gets its own platform

CoreFoundations
Difficulty

The story

Northwind runs an ERP and a WMS in each of its four entities. Both are OLTP systems: they read and write a handful of rows by key, thousands of times a second, and keep only the current state. Ask one of them for revenue by entity by month for two years, in euros and you get the opposite workload: scan tens of millions of invoice lines, touch three columns, aggregate, and join to systems that live in other databases. Nothing about the ERP's storage, schema or capacity was built for that question.

So analytics gets its own platform, for three reasons that hold whatever tools you pick. Isolation: a month-end scan on the primary competes with order entry for I/O and buffer cache; on a Postgres replica it is either cancelled by replication conflicts or, with hot_standby_feedback on, holds back vacuum on the primary. Shape: scans want column-oriented storage and denormalised models; transactions want rows and normal forms. History and integration: the ERP overwrites a customer's region and cannot join to the WMS of another entity. The platform keeps every version and is the one place the entities meet.

Trade-off: a replica and some views vs a platform. One source, a few gigabytes, questions only about the present? A read replica with a capped reporting role is a platform, and an honest one. The moment you need a second source, history the source forgets, or a number finance will sign, the replica stops being cheaper. It just moves the cost into spreadsheets.

Use when
  • Two or more source systems must be joined (ERP + WMS per entity)
  • Reports need history the source overwrites
  • Analytical scans are hurting OLTP latency or vacuum
Avoid
  • Pointing BI tools at the production ERP
  • Building a lakehouse before there is a second question to answer
  • Copying OLTP schemas one-to-one and calling it a warehouse

02

Columnar storage and Parquet

CoreStorage
Difficulty

The story

A row store keeps each record together, so reading one column of a 40-column invoice table still drags the other 39 through memory. Parquet turns that around. A file is split into row groups (typically a hundred thousand to a few million rows); inside each row group every column is stored contiguously as a column chunk, made of pages. Each chunk is encoded (dictionary, run-length, bit-packing) and then compressed (Snappy or Zstd). Low-cardinality columns like entity_id or currency_code shrink to almost nothing.

The footer holds the schema and, for every column chunk, statistics: min, max and null count. A reader fetches the footer first (one ranged GET on object storage), drops every row group whose statistics cannot match the filter (predicate pushdown), then fetches only the column chunks the query names (projection pushdown). The catch: statistics only prune when the data is clustered on the filter column. Write Northwind's invoice lines sorted by date and each row group covers a few days; write them in arrival order and every row group spans the whole year, so nothing is skipped.

Trade-off: immutable files vs updates. Parquet files are never edited in place; changing one row means rewriting the file. That is fine for append-mostly facts and painful for late corrections, which is exactly the gap table formats fill. File size matters too: thousands of 1 MB files cost more in requests and footer reads than the data itself. Aim for roughly 128 MB to 1 GB per file and compact the rest.

Use when
  • Wide tables queried a few columns at a time
  • Write once, read many: facts, snapshots, history
  • Exchanging data between engines (Spark, DuckDB, Fabric, Snowflake)
Avoid
  • Row-at-a-time updates or point lookups by key
  • Streaming writers that produce a file per second
  • CSV as the system of record in the lake: no types, no statistics

COPY (
    SELECT *
    FROM silver.invoice_lines
    ORDER BY invoice_date, entity_id      -- sort = tight min/max per row group
) TO 'lake/silver/invoice_lines/2026-10.parquet'

-- Look inside: one row per column chunk, with its statistics.
SELECT row_group_id, path_in_schema, stats_min_value, stats_max_value, compression
FROM parquet_metadata('lake/silver/invoice_lines/2026-10.parquet')
WHERE path_in_schema = 'invoice_date'
ORDER BY row_group_id;

-- The reader uses them: row groups whose max is before the filter are never
-- fetched, and only the invoice_date and amount_rpt chunks are read at all.

SELECT sum(amount_rpt)
FROM read_parquet('lake/silver/invoice_lines/*.parquet')
WHERE invoice_date >= DATE '2026-10-01';
# The same three levers (sort, row-group size, codec) from Python,
# then a read that prunes by statistics and projects two columns.
from datetime import date

import pyarrow.compute as pc
import pyarrow.parquet as pq

lines = lines.sort_by([("invoice_date", "ascending"), ("entity_id", "ascending")])
pq.write_table(
    lines,
    "lake/silver/invoice_lines/2026-10.parquet",
    row_group_size=500_000,
    compression="zstd",
)

meta = pq.ParquetFile("lake/silver/invoice_lines/2026-10.parquet").metadata
date_col = lines.schema.get_field_index("invoice_date")
for i in range(meta.num_row_groups):
    stats = meta.row_group(i).column(date_col).statistics
    print(i, stats.min, stats.max, stats.null_count)

october = pq.read_table(
    "lake/silver/invoice_lines/",
    columns=["invoice_date", "amount_rpt"],               # projection pushdown
    filters=[("invoice_date", ">=", date(2026, 10, 1))],  # predicate pushdown
)
print(pc.sum(october["amount_rpt"]))

03

Object storage as the lake

CoreStorage
Difficulty

The story

Every modern data platform keeps its files in object storage: S3, Azure Blob and ADLS, GCS, or OneLake on top of them. It is cheap, extremely durable and separate from compute, so engines scale up and down without moving data. But it is not a file system, and the differences decide how platforms are built. The namespace is flat: bronze/erp/entity=NW-ZA/… is one key and the slashes are just characters. Objects are written whole and atomically. There is no append (outside special blob types) and, in S3 general-purpose buckets, no rename: a "move" is copy then delete, so renaming a "directory" is thousands of non-atomic operations.

What you do get is strong. S3, Azure Blob and GCS are strongly consistent: a successful write is visible to the next read and list. Ranged GETs let a Parquet reader fetch only the footer and the chunks it needs. Conditional writes (ETag If-Match, create-only If-None-Match) are the compare-and-swap that table formats and idempotent landings build on. Then the protection layer: versioning keeps prior versions on overwrite, soft delete makes deletes recoverable, lifecycle rules tier or expire objects by age and prefix, and object lock (immutability) makes Northwind's raw zone write-once for the auditors.

Trade-off: hierarchical namespace or flat. Azure's ADLS Gen2 hierarchical namespace adds real directories, atomic directory rename and POSIX-style ACLs, which suits Hadoop-era tools that commit by renaming. With a table format, commits are pointer swaps and rename matters much less. Check which data-protection features your account type supports before you choose, because support has differed between flat and hierarchical accounts. And keep the archive tier away from anything a query touches: rehydration takes hours.

Use when
  • The single durable store under every layer
  • Raw landing zones that must stay immutable for audit
  • Decoupling storage from compute so engines can change
Avoid
  • Treating prefixes as directories with atomic rename
  • Listing millions of keys per query: let the table format track files
  • A mutable latest.csv overwritten in place, with no versioning

# Landing writes are create-only: a batch can be retried safely,
# but nothing can silently overwrite what the source already sent.
import hashlib

from azure.core.exceptions import ResourceExistsError
from azure.identity import DefaultAzureCredential
from azure.storage.blob import BlobServiceClient

service = BlobServiceClient(
    account_url="https://nwlake.blob.core.windows.net",
    credential=DefaultAzureCredential(),
)
lake = service.get_container_client("lake")


def land(entity: str, load_date: str, batch_id: str, payload: bytes) -> str:
    key = f"bronze/erp/entity={entity}/load_date={load_date}/{batch_id}.parquet"
    digest = hashlib.sha256(payload).hexdigest()
    try:
        lake.upload_blob(
            name=key,
            data=payload,
            overwrite=False,                 # a conditional create, not a PUT-over
            metadata={"sha256": digest, "batch_id": batch_id},
        )
    except ResourceExistsError:
        existing = lake.get_blob_client(key).get_blob_properties().metadata
        if existing.get("sha256") != digest:
            raise RuntimeError(f"{key} already exists with different content")
        # Same bytes already landed: this is a retry, not a conflict.
    return key

04

Lake, warehouse, lakehouse · medallion layers as contracts

ArchitectureCore
Difficulty

The story

Three storage architectures answer one question: where do the tables live, and who can read them? A warehouse bundles storage, engine and SQL (Snowflake, BigQuery, Synapse dedicated pools, or a well-run Postgres): ACID, fast, simple, and readable only through that engine. A lake is files on object storage: open, cheap, readable by any engine, and without transactions, so concurrent writers, failed jobs and corrections slowly turn it into a swamp. A lakehouse adds a table format and a catalog to the lake and gets warehouse behaviour (ACID, MERGE, schema evolution, time travel) on open files that several engines share.

Medallion layering is orthogonal to all three. Bronze, silver and gold are not products or folders; they are contracts. Bronze promises exactly what the source sent, never edited, replayable. Silver promises typed, deduplicated, keys conformed across entities, one row per version. Gold promises business grain, reconciled to the source, stable names, documented. Northwind's BI and its AI assistant read gold only; analysts may read silver; nothing but the pipeline reads bronze. Enforce it with schemas and grants, and with a CI check that fails when a gold model reaches past silver.

Trade-off: openness vs operational simplicity. A lakehouse avoids lock-in and lets Spark, DuckDB and Power BI read one copy, at the price of running a catalog, compaction and file housekeeping. A warehouse does that work for you and bills you for it. The layers are the same either way: for a few hundred gigabytes, three schemas in one engine is a complete medallion architecture.

Use when
  • Several consumers need different guarantees from the same data
  • You must replay: rebuild silver and gold from bronze after a logic fix
  • Several engines must read one copy (lakehouse)
Avoid
  • "Gold" that is silver with renamed columns
  • Seven layers because a vendor diagram had them
  • Dashboards reading bronze because gold was late

# CI guard: gold may depend only on silver or gold. Fails the build when
# someone "just quickly" points a gold model at a raw source.
import json
import sys
from pathlib import Path

ALLOWED = {"gold": {"gold", "silver"}, "silver": {"silver", "bronze", "seed"}}

manifest = json.loads(Path("target/manifest.json").read_text())


def layer(unique_id: str) -> str:
    if unique_id.startswith("source."):
        return "bronze"
    if unique_id.startswith("seed."):
        return "seed"
    if unique_id.startswith("snapshot."):
        return "silver"
    fqn = manifest["nodes"][unique_id]["fqn"]   # ["northwind", "gold", "fct_..."]
    return fqn[1] if len(fqn) > 2 else "unknown"


violations = []
for uid, node in manifest["nodes"].items():
    if node["resource_type"] != "model":
        continue
    own = layer(uid)
    for parent in node["depends_on"]["nodes"]:
        if own in ALLOWED and layer(parent) not in ALLOWED[own]:
            violations.append(f"{uid} ({own}) -> {parent} ({layer(parent)})")

if violations:
    print("Layer contract broken:\n  " + "\n  ".join(violations))
    sys.exit(1)
print(f"OK: {len(manifest['nodes'])} nodes respect the layers")

Table formats · ACID on files

StorageDeep dive
Difficulty

The story

A folder of Parquet files is not a table. A reader that lists it mid-write sees half a load; a job that dies leaves orphan files that look like data; there is no UPDATE, DELETE or MERGE; two writers can silently clobber each other. Table formats fix this with a metadata layer that says exactly which files make up each version of the table. In Iceberg, a catalog holds a pointer to the current metadata file; that file lists snapshots; each snapshot points to a manifest list, then manifests, then data files, with partition values and column statistics at each level so planning prunes without listing storage. Delta Lake keeps an ordered log of JSON commits with periodic Parquet checkpoints. DuckLake keeps the same kind of metadata in an ordinary SQL database and the data in Parquet.

A commit is optimistic concurrency: write the new data files and manifests, then atomically swap the pointer from the version you started on to the new one. If another writer got there first, the swap fails, and you re-read, re-apply and retry. Readers pin a snapshot, so they never see half a commit, and old snapshots give you time travel: Northwind can re-run September exactly as it stood at close. Iceberg also tracks columns by id (renames are safe) and hides partitioning behind transforms like days(invoice_ts), so queries filter on the real column and still prune.

Trade-off: Iceberg vs Delta, and the housekeeping bill. Pick the format your engines speak natively: Fabric and Databricks are Delta-first, while Snowflake, AWS and most open engines lean Iceberg. Interop features exist, but one primary format per table is simpler. Either way you now own maintenance: compaction of small files, snapshot expiry (time travel only reaches as far back as retention) and orphan cleanup. Skip them and storage grows forever while queries slow down.

Use when
  • Lakehouse tables that need MERGE, deletes or corrections
  • Several engines must read and write one copy
  • Audit asks for the numbers exactly as reported on close day
Avoid
  • Hand-rolled "write to _tmp, then rename" commits on object storage
  • Running without compaction and snapshot expiry
  • Two formats for one table because two teams disagreed
Connects to Parquet, Object storage, Orchestration, ACID, MVCC

# Readers pin a snapshot: a commit landing mid-read changes nothing for them.
pinned = table.current_snapshot().snapshot_id
za = table.scan(
    row_filter=EqualTo("entity_id", "NW-ZA"),

# Writers commit optimistically: new files, then one atomic pointer swap.
def append_batch(batch: pa.Table, attempts: int = 3) -> None:
    for _ in range(attempts):
        try:
            table.append(batch)
            return
        except CommitFailedException:
            table.refresh()     # someone else won: re-base on their snapshot, retry
    # Files written by lost attempts are orphans; remove_orphan_files sweeps them.
    raise RuntimeError(f"gave up after {attempts} commit conflicts")


for snap in table.snapshots():
    print(snap.snapshot_id, snap.timestamp_ms, snap.summary)

Ingestion · full, incremental, CDC, push vs pull

IntegrationCore
Difficulty

The story

Every pipeline extracts in one of three ways. A full extract copies the whole table each run: trivial, and it sees deletes, but its cost grows with the table. An incremental extract pulls rows whose updated_at is past a stored watermark: cheap, but blind to hard deletes, dependent on every write path setting updated_at (make it a database trigger, not application code), and in need of a lookback so rows committed late by long transactions are not skipped. CDC reads the database's own log (WAL, binlog, SQL Server change tables): every insert, update and delete in order, at the price of log access, replication-slot care and schema-change events. Northwind uses full for small reference tables, incremental for most ERP tables, and CDC for stock movements, where deletes and ordering matter.

The second decision is the network boundary. Several of Northwind's entity ERPs run on-premises at a depot. Pull means a cloud connector reaches in, which needs an inbound path: VPN, private connectivity, or a firewall rule someone has to own. Push means an agent beside the ERP extracts and sends outbound over HTTPS to a landing container, so the firewall only allows outbound 443. A self-hosted integration runtime is the hybrid: the agent opens the connection outbound, then the cloud tells it what to fetch. The real question is not who moves the bytes but who opens the connection.

Trade-off: exactly-once delivery vs idempotent loads. You will not get exactly-once across a network; you can make duplicates harmless. Land each batch under a deterministic key, append it to bronze, and MERGE into silver by business key so the newest source version wins. Advance the watermark only after the load commits, ideally in the same transaction. Re-running a batch, or overlapping two, then converges on the same table.

Use when
  • Incremental with a lookback where updated_at is trustworthy
  • CDC when deletes, ordering or near-real-time matter
  • Push agents when the source sits behind a firewall you cannot open inbound
Avoid
  • Advancing the watermark before the load commits
  • Trusting an updated_at that only some code paths set
  • Claiming exactly-once instead of building an idempotent MERGE
Connects to Change Data Capture, Idempotency, Dual writes, Transactional Outbox, Secrets management

Dimensional modelling · grain, facts, conformed dimensions, SCD2

ModellingCore
Difficulty

The story

Dimensional modelling starts with one sentence: the grain. For Northwind's sales fact it is one row per posted invoice line. Every column must be true at that grain, and every question asked of the table must make sense at it. Facts are the measurements: quantity and amount are additive (sum across anything), stock on hand is semi-additive (sum across warehouses, never across days), margin percentage is non-additive (store the parts, compute the ratio last). Dimensions are the context you group and filter by: date, customer, product, entity.

Conformed dimensions are what make a multi-entity group reportable. Each entity's ERP has its own product codes and the WMS has others; mapping them to one group SKU in a dim_product shared by the sales and shipments facts is what lets finance drill across entities and systems with one filter. Currency works the same way: keep the transaction amount and currency, add the reporting amount and the rate used, so month-end can be reproduced and audited. SCD type 2 keeps attribute history: when a customer moves from the inland to the coastal region, the old row is closed and a new version opens with a new surrogate key. Facts join to the version valid on the invoice date, so last year's regional sales stay last year's.

Trade-off: star schema vs one big table. A wide, denormalised table per report is quick to build, fast in a BI engine and fine for a single consumer. A star with conformed dimensions costs more design up front but gives one definition of customer and product across every fact, which is what a group with four ERPs needs. Many teams do both: a star in gold, with wide marts generated from it.

Use when
  • The business asks "by what?" across several sources
  • Attributes change and history must report as it was (SCD2)
  • Multi-currency facts that must reproduce month-end exactly
Avoid
  • Modelling from source tables instead of from the grain
  • Mixing grains in one fact (lines and invoice headers)
  • Type 1 overwrites where finance needs history
Connects to Medallion layers, Reconciliation, Semantic layer, Schema evolution

# SCD type 2 by hand, to see exactly what the tools do for you.
from dataclasses import dataclass, replace
from datetime import date

OPEN_END = date(9999, 12, 31)
TRACKED = ("region", "segment", "credit_terms")


@dataclass(frozen=True)
class CustomerVersion:
    customer_sk: int
    customer_key: str
    region: str
    segment: str
    credit_terms: str
    valid_from: date
    valid_to: date = OPEN_END

    @property
    def is_current(self) -> bool:
        return self.valid_to == OPEN_END


def apply_scd2(current: dict[str, CustomerVersion], incoming: list[dict],
               as_of: date, next_sk: int) -> list[CustomerVersion]:
    """Return the rows to write: closed old versions plus new open ones."""
    changes: list[CustomerVersion] = []
    for row in incoming:
        old = current.get(row["customer_key"])
        if old and all(getattr(old, col) == row[col] for col in TRACKED):
            continue                                      # nothing tracked changed
        if old:
            changes.append(replace(old, valid_to=as_of))  # close the old version
        changes.append(CustomerVersion(
            customer_sk=next_sk,                          # new surrogate key
            customer_key=row["customer_key"],
            valid_from=as_of,
            **{col: row[col] for col in TRACKED},
        ))
        next_sk += 1
    return changes

Orchestration · assets, partitions, backfills

OperationsCore
Difficulty

The story

Cron and scripts become a task graph quickly: extract, then load, then transform. A task-oriented orchestrator knows that a task exited zero; it does not know whether gold.fct_invoice_lines is current. An asset-oriented one (Dagster's software-defined assets, dbt's model graph, Airflow's datasets and assets) starts from the data products and their dependencies. It records when each asset was materialised, from which code version and which upstream data, so it can answer the questions that matter at 07:00: what is stale, why, and what must re-run.

Partitions make runs addressable. Northwind partitions by day and entity, so every run materialises exactly one cell, say 2026-10-06 × NW-NL, and replaces it. Because each partition overwrites itself, a retry is safe and a backfill is just a range of partitions run with bounded concurrency, so the source ERP is not hammered. Late-arriving data becomes routine: re-run the last three days every night. When finance re-opens September, re-materialise September's partitions and publish atomically.

Trade-off: Dagster vs Airflow vs managed pipelines. Dagster is asset-first and strong on partitions and lineage; Airflow is everywhere and has moved toward assets; ADF and Fabric pipelines are managed and fit the rest of Azure, but version control and testing take more discipline. Whichever you choose, keep business logic in SQL and Python modules that the orchestrator calls, not inside the orchestrator, so you can test it and, one day, leave.

Use when
  • More than a handful of jobs with dependencies between them
  • Backfills, reprocessing and late data are normal, not incidents
  • You need lineage: which dashboard breaks if this source is late?
Avoid
  • Runs that append, so a retry doubles the numbers
  • Backfills with unbounded concurrency against a production source
  • Transformation logic written inside orchestrator callbacks
Connects to Idempotent loads, Freshness, Idempotency, Retry with backoff

Correctness · reconciliation, contracts, freshness

QualityCore
Difficulty

The story

Tests like not_null and unique check the shape of data. They cannot tell you that September revenue is short by one entity's credit notes. Reconciliation can. Extract control totals that the source itself computes (counts and sums by entity, period, currency and, for finance, GL account) alongside the data, and compare them with the same totals computed from gold on every load. In transaction currency the difference must be exactly zero; in reporting currency, within rounding. Zero publishes; anything else blocks the publish and pages the owner. Northwind's month-end pack is released only when gold ties to each entity's trial balance.

Data contracts move quality upstream. A contract is an agreement with the producing team about schema, keys, meaning and units, allowed values, freshness and an owner, plus a change process: versioned, announced, never a surprise column rename on a Friday. Enforce it at both ends: the producer's CI checks what it emits, and ingestion quarantines anything that breaks it rather than loading it. Freshness is health: set an SLO such as yesterday's sales in gold by 06:00 on 99% of days, measure it from the newest source change included rather than the job's finish time, and alert on that. A pipeline that ran green and loaded zero rows is not healthy.

Trade-off: strictness vs availability. Blocking a publish on any difference can hold everyone up over a single cent. Decide per dataset: finance facts block on any difference; operational dashboards may publish with a visible warning and a ticket. What never works is quietly publishing numbers you could have proven wrong.

Use when
  • Anything finance signs or an auditor reads
  • Sources owned by other teams that change without telling you
  • Dashboards people act on before 09:00
Avoid
  • Tests as a substitute for reconciliation
  • Alerting on job failure only: a green job can load nothing
  • Control totals computed by the platform on both sides

Serving · marts, semantic layer, atomic publish, build vs buy

ServingArchitecture
Difficulty

The story

Gold is not yet a product. Marts cut it into narrow, named datasets for one audience: finance, operations. A semantic layer defines each metric once (revenue, gross margin, on-time-in-full) with its measures, dimensions and filters, and every consumer asks for the metric by name: the BI tool, the finance exports, and Northwind's AI assistant, which calls governed metric tools with the caller's entity scope instead of writing SQL against silver. Atomic publish means consumers see yesterday's release or today's, never half of each: build into gold_next, reconcile, then swap in one step (a schema rename in a transaction, Snowflake's SWAP WITH, or a single table-format commit).

For BI the key serving choice is import vs DirectQuery. Import copies data into the BI engine: very fast, but stale between refreshes and bounded by model size. DirectQuery sends each visual's query to the source at view time: fresh, but every click is a query, so the source must be sized for it, and row-level security has to hold there. Fabric's Direct Lake mode reads Delta tables in OneLake straight into the Power BI engine, close to import speed without a separate copy, which is a large part of Fabric's appeal to an organisation that already runs on Power BI.

Trade-off: build vs buy. Self-run (DuckDB or Postgres, dbt, Dagster, object storage, containers) has the lowest bill and the highest attention cost: you are the vendor, and you are on call. Fabric fits an organisation already on Microsoft 365 and Power BI: one capacity, OneLake, Direct Lake, less to operate, and capacity sizing to watch. Databricks or Snowflake earn their price with scale, many teams, ML and mature governance. For Northwind, with a few hundred gigabytes and a two-person data team, the honest shortlist is self-run or Fabric. Open table formats keep the exit door open whichever you pick.

Stream processing · event time, windows, watermarks, state

StreamingDeep dive
Difficulty

The story

Batch answers what happened yesterday; stream processing answers while it is still happening. Northwind's cold rooms and reefer trucks report a temperature every 30 seconds, and a vaccine consignment is written off if a unit stays above 8 °C for ten minutes. A 06:00 batch is useless for that. A stream job computes continuously over an unbounded, ordered log (Kafka, Event Hubs), and three ideas make the answer right. Event time vs processing time: window by when the reading was taken, not when it arrived. A truck that crosses a dead zone uploads twenty minutes of buffered readings at once; windowed by arrival, they all land in the wrong bucket. Windows cut the endless stream into finite groups: tumbling (fixed, no overlap), sliding or hopping (fixed, overlapping) and session (closed by a gap in activity). Watermarks are the job's claim that it has probably seen everything up to time T, usually the newest event time minus a bound on lateness. When the watermark passes the end of a window, the window emits. Readings later than the watermark plus the allowed lateness go to a side output, never silently dropped, and the batch layer corrects for them.

State and checkpoints. A window, or a rule like ten minutes above 8 °C, needs memory per key: per unit. The engine keeps it in a local state store partitioned like the topic, and periodically checkpoints the state together with the input offsets. After a crash it restores both and replays from the checkpoint, so the results are as if nothing failed: effectively once. That promise ends at the engine's edge. A sink that is neither transactional nor idempotent, such as a webhook that pages someone, will see duplicates after a restart, so give every side effect a deterministic key (unit plus window start) and let the sink ignore repeats. It is the same discipline as idempotent landing in ingestion.

Trade-off: stream vs micro-batch vs batch. Streaming costs always-on compute, state you have to operate and upgrade, harder reprocessing, and time-based logic that is hard to test. Start from the real freshness SLO. Seconds (a cold-chain breach, card fraud, stock reservations) justify a stream. Minutes are a micro-batch every few minutes. Hours are batch. Among engines, Flink is the most complete on event time and state; Kafka Streams is a library inside your own service with no cluster to run; Spark Structured Streaming fits where Spark already runs; Azure Stream Analytics and Fabric Real-Time Intelligence are the managed options in a Microsoft estate. The common shape is stream for the alert, batch for the books: the stream also lands raw events in bronze, and finance numbers are still reconciled in batch.

Use when
  • The freshness SLO is seconds, not hours
  • Acting on events: alerts, fraud, reservations
  • Continuous aggregates feeding an operations screen
Avoid
  • Streaming because it sounds modern when the SLO is 06:00
  • Processing-time windows over data that devices buffer
  • Dropping late events silently
  • Trusting "exactly-once" in front of a non-idempotent sink

@app.post("/alerts/cold-chain", status_code=status.HTTP_202_ACCEPTED)
async def cold_chain_breach(b: Breach) -> dict:
    alert_id = f"{b.unit_id}:{b.window_start.isoformat()}"   # deterministic key
    async with app.state.pool.acquire() as con, con.transaction():
        inserted = await con.fetchval(
            """
            INSERT INTO alerts (alert_id, unit_id, window_start, min_temp_c)
            VALUES ($1, $2, $3, $4)
            ON CONFLICT (alert_id) DO NOTHING
            RETURNING alert_id

            await con.execute(
                "INSERT INTO outbox (topic, key, payload) VALUES ('page.on-call', $1, $2)",
                alert_id, b.model_dump_json(),
            )
    return {"alert_id": alert_id, "duplicate": inserted is None}

Data observability · volume, schema, distribution, lineage

QualityOperations
Difficulty

The story

Reconciliation proves one release is right. Data observability tells you something is going wrong across hundreds of tables before anyone asks. It is the data platform's version of the golden signals, and it watches five things on every run. Freshness: the newest source change included, against its SLO. Volume: row counts against what this table usually gets on this kind of day. Schema: a column added, dropped, renamed or retyped since the last run. Distribution: null rates, ranges and category mix, such as a currency column that is suddenly a third USD. Lineage: which upstream change caused this, and which downstream tables, dashboards and assistant answers are now wrong. Tests check what you thought to write down; observability catches what you did not. When Northwind's Kenyan ERP is upgraded and renames the discount field, freshness is green and volume is normal, but the null rate on discount_pct jumps from 2% to 100%, and the margin dashboards drift quietly.

The mechanics are cheap. Record a few numbers per table on every run (row count, null rate per key column, min and max, a hash of the column list) into a metrics table, mostly from statistics the run already has. Compare each against a seasonality-aware baseline, such as the same weekday over the last four weeks, not a fixed threshold, because Monday loads are not Sunday loads. Route each alert by ownership from the catalog, and attach the blast radius from lineage, so the message reads erp_ke.invoice_lines changed schema; three dashboards and the assistant's margin tool are affected rather than test failed. Lineage comes free from dbt's manifest or the orchestrator's asset graph; keep it there, not in a diagram nobody updates.

Trade-off: coverage vs alert fatigue. Anomaly detection on every column of every table produces noise, and a team that has learned to ignore alerts is worse off than one with five good ones. Start with freshness, volume and schema on tier-1 datasets (anything finance signs or the assistant reads), and add distribution checks where an incident has shown the need. Buy a platform (Monte Carlo, Databricks Lakehouse Monitoring, Purview data quality) when tables number in the hundreds and many teams own them. For Northwind, dbt tests plus a small metrics table, or the open-source elementary package, cover it.

Use when
  • Sources owned by teams who change them without notice
  • More tables than people can eyeball
  • Data feeding decisions or an AI assistant before 09:00
Avoid
  • Fixed thresholds on seasonal volumes
  • Alerts without an owner or a blast radius
  • Anomaly detection on everything from day one
  • Lineage kept by hand in a slide

@app.get("/lineage/{asset}/impact")
def impact(asset: str) -> dict:
    if asset not in LINEAGE and asset not in OWNERS:

    seen, queue = set(), deque([asset])
    while queue:                                 # breadth-first, downstream only

            if child not in seen:
                seen.add(child)
                queue.append(child)
    affected = sorted(seen)
    return {
        "asset": asset,
        "affected": affected,
        "notify": sorted({OWNERS[a] for a in affected if a in OWNERS}),
        "tier_1": [a for a in affected if a.startswith(("gold.", "mart_", "dashboard."))],
    }

Governance · classification, masking, ownership, access audit

SecurityArchitecture
Difficulty

The story

Security protects the systems; governance decides who may see which data, and proves it afterwards. It has four parts. Classify: give every column a sensitivity label (internal, confidential, personal), because personal information under POPIA, such as Northwind's driver ID numbers and phone numbers in the WMS or payroll in the ERP, carries legal duties. Own: every dataset has an owner and a steward, recorded in a catalog (Purview, Unity Catalog) alongside its lineage and definitions. Control: role-based grants on schemas, row-level security so the Kenyan team sees Kenyan rows, and column masking so analysts see *********4087 where HR sees the full ID. Audit: record who read what, when, why and how many rows, especially for personal data and for every AI assistant tool call.

Attach policy to the label, not the table. Tag national_id as pii.national_id once, and the masking policy follows it into every table derived from it; Unity Catalog and Purview can propagate tags along lineage. There are three ways to protect a value. Dynamic masking stores the value in the clear and hides it at query time: fine for analysts, useless against anyone who can read the files. Tokenisation or pseudonymisation replaces the value at rest with a deterministic token, so joins still work; use it for data that leaves the platform and for development copies. Minimisation is the strongest: the bronze contract names which personal fields are needed, and the rest are never loaded. Erasure requests meet table formats here: deleting a driver from an Iceberg or Delta table leaves them in old snapshots until those expire, so set snapshot retention with the privacy policy in mind.

Trade-off: central control vs federated ownership. A central team cannot classify every column on a growing platform, and domain teams do not know the policy. The usual answer is central policies and labels, domain owners who apply them, and CI that enforces them: a new gold column without a classification fails the build. Remember that masking and row-level security are engine controls. Anyone with direct access to the lake's storage account bypasses them, so lock storage down until the query engines are the only path to the data.

Use when
  • Personal or regulated data on the platform (POPIA, GDPR, PCI)
  • Several entities or teams share one platform
  • An AI assistant or a partner queries the data
Avoid
  • Masking only in the BI tool while the lake files stay open
  • Policies hand-copied table by table
  • Production personal data in development copies
  • A classification spreadsheet nobody updates
