Order fulfilment
Backend katas / Applied system design
Applied system design · Interview prep

Ship it. Track everything.

An order isn't complete when the customer clicks "buy" — it's complete when the package is on their doorstep. Between those two moments: inventory reservation, warehouse assignment, picking, packing, shipping, tracking, delivery, and returns. Every step is a state machine, every handoff is a failure point, and every delay is a customer calling support.

LanguagesGo · Python · TypeScript
PRINCIPLE 01

Reserve, don't deduct.

Inventory is reserved at checkout and deducted at ship confirm. The gap prevents overselling while allowing cancellation.

PRINCIPLE 02

Every handoff is a contract.

Warehouse → carrier → hub → last-mile. Each handoff is a scan event. Missing scans mean lost packages and blind spots.

PRINCIPLE 03

Optimise for the 99%, handle the 1%.

Most orders ship normally. Design the happy path to be fast and the exception path (returns, damaged, address correction) to be survivable.

PRINCIPLE 04

Location is a first-class entity.

Warehouses, hubs, drivers, customers — everything has coordinates. Geospatial indexing isn't optional, it's the foundation.

01

High-level architecture & order lifecycle

Start hereArchitecture
Difficulty

The story

An order flows through six stages: place (reserve inventory, capture payment), assign (pick the optimal warehouse), pick+pack (warehouse workers scan items), ship (generate label, hand off to carrier), transit (tracking events from carrier scans), and deliver. Each stage is owned by a different service. The order service orchestrates the saga; inventory, warehouse, and tracking services handle their domains independently.

Trade-off: monolith vs microservices for fulfilment. Early-stage companies should start with a monolith — splitting too early means distributed transactions before you understand the domain. At scale, split on domain boundaries: inventory is a separate bounded context from warehouse operations. The critical insight: inventory (how much do we have?) and warehouse (where is it physically?) are different services even though they seem related.

Key components
  • Order service: saga orchestrator, state machine, source of truth
  • Inventory: stock levels, reservations, restock events
  • Tracking: event-sourced timeline, CQRS read model, push notifications
Interview red flags
  • Deducting inventory at checkout (should reserve, deduct at ship)
  • No state machine for order lifecycle
  • Polling carrier APIs instead of event-driven tracking
Connects to Saga, Event sourcing
Real-world: Shopify — Building the Fulfilment Network · Grab — Scaling order management

02

Inventory reservation & oversell protection

CoreCritical
Difficulty

The story

available = physical − reserved. At checkout, you reserve stock (increment the reserved counter). At ship confirm, you deduct physical stock. If the order is cancelled or the reservation expires (15-minute TTL), you release the reservation. This prevents overselling: two concurrent buyers both see "1 in stock," but only one's reservation succeeds because the UPDATE uses a WHERE clause that checks availability atomically.

Trade-off: Postgres atomic UPDATE vs Redis DECR. For most e-commerce (<5k orders/second), a Postgres UPDATE inventory SET reserved = reserved + 1 WHERE (physical - reserved) >= $qty with row-level locking is sufficient, simple, and ACID. For flash sales (100k+ concurrent), use Redis DECR as a fast gate (reject immediately if sold out) backed by async DB sync. Shopify uses a hybrid: Redis for the hot check, Postgres for the source of truth, reconciled every few seconds.

Design decisions
  • Reserve at checkout, deduct at ship — never deduct early
  • Reservation TTL (15min) — auto-release abandoned carts
  • Atomic WHERE clause or Redis DECR for concurrency
Traps
  • Deducting stock at checkout — cancellation logic becomes nightmarish
  • SELECT then UPDATE (TOCTOU race) — use atomic operations
  • No reservation expiry — ghost reservations eat your inventory
Connects to Transactions, Hot keys
Real-world: Shopify — Surviving flash sales
// Atomic reservation — single UPDATE, no race condition.
func (r *InventoryRepo) Reserve(ctx context.Context, sku string, qty int) error {
    res, err := r.db.Exec(ctx, `
        UPDATE inventory
           SET reserved = reserved + $1
         WHERE sku = $2
           AND (physical - reserved) >= $1   -- atomic check
    `, qty, sku)
    if err != nil { return err }
    if res.RowsAffected() == 0 {
        return ErrOutOfStock     // no rows matched → insufficient stock
    }
    return nil
}

// Release expired reservations (cron every minute)
func (r *InventoryRepo) ReleaseExpired(ctx context.Context) {
    r.db.Exec(ctx, `
        UPDATE inventory i SET reserved = reserved - r.qty
        FROM reservations r
        WHERE r.sku = i.sku AND r.expires_at < NOW() AND r.status = 'active'
    `)
}

from fastapi import FastAPI, HTTPException, Request
from pydantic import BaseModel, Field

class ReserveIn(BaseModel):
    order_id: str
    sku: str
    qty: int = Field(gt=0)

app = FastAPI(lifespan=lifespan)  # lifespan opens redis.asyncio + Kafka producer

@app.post("/reservations", status_code=201)
async def reserve_fast(body: ReserveIn, request: Request) -> dict:
    redis, kafka = request.app.state.redis, request.app.state.kafka
    # Atomic decrement — if result goes below 0, roll back
    remaining = await redis.decrby(f"stock:{body.sku}", body.qty)
    if remaining < 0:
        await redis.incrby(f"stock:{body.sku}", body.qty)  # roll back
        raise HTTPException(409, "out of stock")
    # Publish event for DB sync
    await kafka.produce("inventory.reserved",
        {"sku": body.sku, "qty": body.qty, "order_id": body.order_id})
    return {"order_id": body.order_id, "remaining": remaining}
// pg — pessimistic lock for reservation, in an explicit transaction.
export async function reserve(sku: string, qty: number): Promise<void> {
    const tx = await pool.connect();
    try {
        await tx.query("BEGIN");
        const { rowCount } = await tx.query(`
            UPDATE inventory SET reserved = reserved + $1
            WHERE sku = $2 AND (physical - reserved) >= $1
        `, [qty, sku]);
        if (rowCount === 0) throw new OutOfStockError(sku);
        await tx.query("COMMIT");
    } catch (err) {
        await tx.query("ROLLBACK");
        throw err;
    } finally { tx.release(); }
}
03

Warehouse assignment & routing

CoreGeospatial
Difficulty

The story

When an order is placed, the system must pick which warehouse fulfils it. The naive answer is "nearest warehouse with stock," but real systems use a scoring function: distance to customer (shipping speed), shipping cost (some lanes are cheaper), warehouse load (don't overload one facility), and whether the warehouse has all items (split shipments are expensive). The query: filter warehouses that have stock, score each, pick the best.

Trade-off: single-warehouse vs split shipment. If one warehouse has item A and another has item B, do you ship from both (faster, higher cost) or wait for a restock (slower, cheaper)? Most systems set a threshold: split only if the cost difference is below X%. Some advanced systems (Amazon) pre-position inventory to minimise splits using demand forecasting.

Design decisions
  • PostGIS ST_Distance or H3 hex index for geospatial queries
  • Weighted scoring: distance + cost + capacity
  • Split shipment only below cost threshold
Traps
  • Always picking nearest — ignores cost and capacity
  • No split shipment logic — some orders become unfulfillable
  • Hardcoded warehouse assignment — doesn't scale with new facilities
Connects to Geospatial, Inventory
Real-world: Zalando — Logistics optimisation
// PostGIS query: nearest warehouse with stock for all SKUs.
func AssignWarehouse(ctx context.Context, db *pgxpool.Pool,
    items []OrderItem, addr Address) (string, error) {

    row := db.QueryRow(ctx, `
        SELECT w.id,
               ST_Distance(w.location, ST_Point($1,$2)::geography) AS dist_m
          FROM warehouses w
         WHERE w.operational = true
           AND NOT EXISTS (
               SELECT 1 FROM unnest($3::text[], $4::int[]) AS t(sku, qty)
                WHERE NOT EXISTS (
                    SELECT 1 FROM inventory i
                     WHERE i.warehouse_id = w.id AND i.sku = t.sku
                       AND (i.physical - i.reserved) >= t.qty
               ))
         ORDER BY dist_m ASC
         LIMIT 1
    `, addr.Lng, addr.Lat, skus(items), qtys(items))
    var whID string
    var dist float64
    return whID, row.Scan(&whID, &dist)
}

@app.post("/orders/{order_id}/assign")
async def assign_warehouse(order_id: str, body: AssignIn, db: Conn) -> dict:
    skus = [i.sku for i in body.items]
    qtys = [i.qty for i in body.items]
    row = await db.fetchrow("""
        SELECT w.id FROM warehouses w
        WHERE w.operational
          AND (SELECT bool_and(
                 (SELECT (physical - reserved) >= qty
                    FROM inventory WHERE warehouse_id = w.id AND sku = t.sku))
               FROM unnest($3::text[], $4::int[]) AS t(sku, qty))
        ORDER BY ST_Distance(w.location, ST_Point($1,$2)::geography)
        LIMIT 1
    """, body.lng, body.lat, skus, qtys)
    if row is None:
        raise HTTPException(409, "no warehouse has stock for every item")
    return {"order_id": order_id, "warehouse_id": row["id"]}
// pg + native PostGIS query.
export async function findNearestWithStock(
    orderId: string, lat: number, lng: number,
): Promise<string | undefined> {
    const { rows } = await pool.query<{ id: string }>(`
        SELECT w.id FROM warehouses w
        WHERE w.operational = true
          AND NOT EXISTS (
              SELECT 1 FROM order_items oi WHERE oi.order_id = $1
              AND NOT EXISTS (
                  SELECT 1 FROM inventory i
                  WHERE i.warehouse_id = w.id AND i.sku = oi.sku
                    AND (i.physical - i.reserved) >= oi.quantity))
        ORDER BY ST_Distance(w.location, ST_Point($2, $3)::geography)
        LIMIT 1
    `, [orderId, lng, lat]);
    return rows[0]?.id;
}
04

Order state machine & fulfilment saga

CoreArchitecture
Difficulty

The story

The order state machine has 10 states and guarded transitions. The fulfilment saga orchestrates the multi-step process: reserve → capture payment → assign warehouse → create shipment → notify. Each step has a compensation. If step 3 fails, run compensations for steps 2 and 1 in reverse. A cancel at any point triggers compensations for all completed steps.

Trade-off: immediate cancel vs graceful cancel. If the order is in picking state, can you cancel? Immediate cancel means the warehouse worker scanned items for nothing. Graceful cancel waits until the current step completes, then reverses. Most systems allow cancel until packed, and refuse after shipped (that becomes a return).

Design decisions
  • Orchestrator (Temporal) owns the saga, persists state
  • Cancel allowed until packed, after = return flow
  • Every step emits domain events for downstream consumers
Traps
  • Cancel after ship = customer confusion (use return instead)
  • No compensation for warehouse assignment
  • State transitions via direct DB updates instead of state machine
Connects to Payment state machine, Saga
Real-world: DoorDash — Building the Order Platform

    InTransit: {Delivered},
    Delivered: {Returned},
}

// Temporal workflow for fulfilment saga
func FulfilmentWorkflow(ctx workflow.Context, order Order) error {
    saga := NewSaga()
    saga.AddStep(ReserveInventory, ReleaseInventory)
    saga.AddStep(CapturePayment, RefundPayment)
    saga.AddStep(AssignWarehouse, UnassignWarehouse)
    saga.AddStep(CreateShipment, CancelShipment)
    return saga.Execute(ctx, order)
}
# Fulfilment saga — sequential with compensations.
from fastapi import FastAPI, BackgroundTasks, HTTPException

TRANSITIONS = {
    "placed":    ["reserved", "cancelled"],
    "reserved":  ["assigned", "cancelled"],
    "assigned":  ["picking", "cancelled"],
    "picking":   ["packed", "cancelled"],
    "packed":    ["shipped"],
    "shipped":   ["in_transit"],
    "in_transit": ["delivered"],
    "delivered": ["returned"],
}

class FulfilmentSaga:
    steps = [
        (reserve_inventory, release_inventory),
        (capture_payment,   refund_payment),
        (assign_warehouse,  unassign_warehouse),
        (create_shipment,   cancel_shipment),
    ]

    async def run(self, order) -> None:
        undo = []
        try:
            for action, compensate in self.steps:
                await action(order)
                undo.insert(0, compensate)  # newest first
        except Exception:
            for compensate in undo:
                await compensate(order)
            raise

@app.post("/orders/{order_id}/fulfil", status_code=202)
async def fulfil(order_id: str, tasks: BackgroundTasks) -> dict:
    order = await orders.get(order_id)
    if "reserved" not in TRANSITIONS.get(order.state, []):
        raise HTTPException(409, f"cannot fulfil an order that is {order.state}")
    tasks.add_task(FulfilmentSaga().run, order)  # runs after the 202 is sent
    return {"order_id": order_id, "status": "fulfilling"}
// Same saga pattern as payment, applied to fulfilment.
export async function fulfil(order: Order): Promise<Order> {
    const comps: Array<() => Promise<void>> = [];
    try {
        await inventory.reserve(order);
        comps.unshift(() => inventory.release(order));
        await payment.capture(order);
        comps.unshift(() => payment.refund(order));
        await warehouse.assign(order);
        comps.unshift(() => warehouse.unassign(order));
        await shipping.create(order);
        return order;
    } catch (err) {
        for (const undo of comps) await undo();
        throw err;
    }
}

Real-time tracking & geospatial indexing

CoreGeospatial
Difficulty

The story

Every scan (warehouse pick, hub arrival, out-for-delivery, delivered) is a tracking event published to Kafka. A consumer enriches each event (resolve driver location to address, calculate ETA), writes to an Elasticsearch read model, and triggers push notifications. The customer-facing app queries ES for the tracking timeline — CQRS in action: writes go to Kafka (event log), reads come from ES (optimised query model).

H3 (Uber's hexagonal grid system) is the geospatial index: every lat/lng maps to a hex cell at various resolutions. "Find all drivers within 2km" becomes "find all drivers in this hex and its k-ring neighbours" — a constant-time index lookup instead of a distance calculation against every driver. Used by Uber, Bolt, DoorDash for dispatch and ETA.

Design decisions
  • Kafka for tracking events, ES for read model (CQRS)
  • H3 hex index for "find nearby" at O(1) per point
  • Push notifications via WebSocket or Firebase on state change
Traps
  • Polling carrier APIs every 30s — use webhooks from carriers
  • PostGIS radius queries on millions of live drivers — use H3
  • Single tracking table in Postgres — won't scale to 100k events/s
Connects to Event sourcing, CQRS
Real-world: Uber — H3: hexagonal hierarchical spatial index · DoorDash — Real-time tracking
// H3 — convert lat/lng to hex cell, find nearby drivers.
import "github.com/uber/h3-go/v4"

func NearbyDrivers(lat, lng float64, ring int) []string {
    center := h3.LatLngToCell(h3.LatLng{Lat: lat, Lng: lng}, 9) // res 9 ≈ 100m
    hexes := h3.GridDisk(center, ring)  // k-ring neighbours

    // Redis: each driver publishes their hex to a set
    var drivers []string
    for _, hex := range hexes {
        ids, _ := redis.SMembers(ctx, "drivers:hex:"+hex.String()).Result()
        drivers = append(drivers, ids...)
    }
    return drivers
}

06

ETA estimation

AdvancedML-adjacent
Difficulty

The story

ETA has three components: processing time (how long until the warehouse ships it), transit time (carrier network hub-to-hub), and last-mile (local delivery). V1 is simple: carrier SLA + average warehouse processing. V2 uses historical data: for this specific lane (warehouse → destination zone), what was the p50 and p90 delivery time over the last 30 days? V3 is ML: a gradient-boosted model trained on lane, day-of-week, warehouse backlog, weather, and carrier performance.

Trade-off: accuracy vs simplicity. V1 is a lookup table — ship it day one. V2 is a SQL query — ship it week two. V3 requires an ML pipeline — ship it quarter two. Most companies start with V1 and iterate. The key interview insight: under-promise and over-deliver. Show a range ("3-5 days") at checkout, narrow it as the package progresses.

Design decisions
  • V1: carrier SLA table + warehouse avg processing time
  • V2: p50/p90 from historical lane data (30-day window)
  • Narrow the estimate as package progresses through stages
Traps
  • Single point estimate ("arrives Tuesday") — use a range
  • Not accounting for warehouse backlog
  • Over-engineering ML when a lookup table is 90% as good
Connects to Tracking, Warehouse
Real-world: Uber — DeepETA · Shopify — Delivery date prediction
// V1 ETA: carrier SLA + warehouse processing average.
func EstimateETA(wh Warehouse, carrier string, zone string) ETARange {
    processing := wh.AvgProcessingHours       // e.g. 12h
    transit    := carrierSLA[carrier][zone]  // e.g. {min: 48h, max: 120h}
    return ETARange{
        Min: time.Now().Add(processing + transit.Min),
        Max: time.Now().Add(processing + transit.Max),
    }
}
# V2 ETA: historical lane performance (p50/p90).
from typing import Annotated
import asyncpg
from fastapi import FastAPI, Depends, HTTPException
from pydantic import BaseModel

@app.get("/eta")

                          db: Annotated[asyncpg.Connection, Depends(get_conn)]) -> ETAOut:
    row = await db.fetchrow("""
        SELECT percentile_cont(0.5) WITHIN GROUP (ORDER BY delivery_hours) AS p50,
               percentile_cont(0.9) WITHIN GROUP (ORDER BY delivery_hours) AS p90
          FROM deliveries
         WHERE warehouse_id = $1 AND zone = $2
           AND shipped_at > NOW() - INTERVAL '30 days'
    """, wh_id, zone)
    if row["p50"] is None:  # no deliveries on this lane in 30 days
        raise HTTPException(404, "no delivery history for this lane")
    return ETAOut(min_hours=row["p50"], max_hours=row["p90"])
// V1 ETA: lookup table.
export async function estimate(
    warehouseId: string, carrier: string, zone: string,
): Promise<ETARange> {
    const processing = await warehouseRepo.avgProcessingHours(warehouseId);
    const sla = carrierSLAs.get(carrier, zone);
    const hoursFromNow = (h: number) => new Date(Date.now() + h * 3_600_000);
    return {
        earliest: hoursFromNow(processing + sla.minHours),
        latest: hoursFromNow(processing + sla.maxHours),
    };
}
07

Returns & reverse logistics

OpsPractical
Difficulty

The story

Returns are the fulfilment flow in reverse: customer requests RMA (return merchandise authorisation), ships the item back, warehouse receives and inspects, then either restocks (add back to inventory) or disposes (write-off). The return has its own state machine. Refund is triggered either at ship-back (customer-friendly, Amazon style) or at inspect (lower fraud risk).

Trade-off: refund-on-ship vs refund-on-inspect. Refund-on-ship delights customers but you eat the cost if the item never arrives or arrives damaged. Refund-on-inspect is safer but the 5-10 day wait generates support tickets. Most companies refund-on-ship for trusted customers (high order history) and refund-on-inspect for new accounts.

Design decisions
  • Separate return state machine from order state machine
  • Inspection grades: A (restock), B (discount), C (dispose)
  • Refund timing based on customer trust score
Traps
  • No return state machine — returns tracked in spreadsheets
  • Restocking without inspection — damaged items shipped again
  • No inventory add-back on restock — phantom stock loss
Connects to Ledger (refund = reverse entry), Inventory
// Return processing: inspect → restock or dispose.
func (s *ReturnService) ProcessInspection(ctx context.Context,
    ret *Return, grade InspectionGrade) error {

    switch grade {
    case GradeA:
        // Restock: add back to physical inventory
        s.inventory.AddPhysical(ctx, ret.SKU, ret.Qty)
        ret.State = ReturnRestocked
    case GradeC:
        // Dispose: write off in ledger
        s.ledger.WriteOff(ctx, ret.SKU, ret.Qty)
        ret.State = ReturnDisposed
    }
    // Trigger refund if not already issued
    if !ret.RefundIssued {
        s.payment.Refund(ctx, ret.OrderID, ret.Amount)
    }
    return s.store.Save(ctx, ret)
}

    await returns.save(ret)
    return {"return_id": return_id, "state": ret.state}

export async function processInspection(ret: Return, grade: Grade): Promise<void> {
    const tx = await pool.connect();
    try {
        await tx.query("BEGIN");
        if (grade === Grade.A) {
            await inventory.addPhysical(tx, ret.sku, ret.qty);
            ret.state = ReturnState.RESTOCKED;
        } else {
            await ledger.writeOff(tx, ret.sku, ret.qty);
            ret.state = ReturnState.DISPOSED;
        }
        await returns.save(tx, ret);
        if (!ret.refundIssued)
            await payment.refund(ret.orderId, ret.amount);
        await tx.query("COMMIT");
    } catch (err) {
        await tx.query("ROLLBACK");
        throw err;
    } finally { tx.release(); }
}
08

Event-driven tracking pipeline (CQRS)

ArchitecturePattern
Difficulty

The story

CQRS (Command Query Responsibility Segregation) splits the write model from the read model. Tracking writes: scan events → Kafka → Postgres (event log). Tracking reads: Kafka consumer projects events into Elasticsearch (denormalised timeline per order). The API queries ES for "show me tracking for order X" — which returns a pre-built timeline with no JOINs. This scales the write path (100k events/sec to Kafka) independently from the read path (fast ES queries).

Trade-off: eventual consistency. The ES read model is seconds behind the Postgres source of truth. For tracking, this is acceptable — a 2-second delay on "your package is at hub X" doesn't matter. For inventory or payments, it wouldn't be. Know where eventual consistency is tolerable and where it isn't.

Design decisions
  • Kafka as event log (write) → ES as read model (query)
  • Projector service: Kafka consumer → denormalise into ES
  • Rebuild read model by replaying Kafka from offset 0
Traps
  • CQRS for everything — overkill for simple CRUD
  • No replay capability — can't rebuild a corrupted read model
  • Treating ES as source of truth (it's a projection, not the source)
Connects to CQRS, Event sourcing

async def lifespan(app: FastAPI):
    consumer = AIOKafkaConsumer("tracking-events", bootstrap_servers=KAFKA)
    await consumer.start()
    async def project():  # write side: Kafka → ES, inside the API process
        async for msg in consumer:
            await handle_tracking_event(msg)
    task = asyncio.create_task(project())
    yield
    task.cancel()
    await consumer.stop()
