Applied system design · Interview prep

Move money. Lose nothing.

A payment system is a distributed ledger where every bug is someone's missing money. Idempotency isn't optional — it's existential. State machines aren't academic — they're the only thing between you and double-charging a customer. This page walks through the full payment lifecycle the way a senior engineer would design it in an interview.

PRINCIPLE 01

The ledger is the source of truth.

Not the database row. Not the API response. The append-only, double-entry ledger. Everything else is a projection.

PRINCIPLE 02

Exactly-once or exactly-zero.

A payment processed twice is worse than a payment not processed at all. Idempotency keys on every mutating call.

PRINCIPLE 03

Design for failure in the middle.

The network will die between authorise and capture. Your system must recover to a consistent state without human intervention.

PRINCIPLE 04

Reconcile everything.

Your ledger and the bank's ledger will drift. Nightly reconciliation isn't a nice-to-have — it's how you find the bugs that logs can't.

01

High-level architecture & payment lifecycle

Start hereArchitecture
Difficulty

The story

A payment isn't one event — it's a lifecycle. The customer checks out, the merchant creates a payment intent, the system authorises against the card network (reserving funds on the customer's card), and later captures (actually moving the money). Settlement happens in batch (T+1 or T+2), and eventually funds are paid out to the merchant. Auth and capture are separate because the merchant might not ship for days — you hold the reservation, not the money.

Trade-off: auth+capture split vs single charge. Split gives you a refund window and prevents charging for unshipped goods (required by card network rules for physical goods). Single charge is simpler and fine for digital goods. Most payment APIs (Stripe, Adyen) support both. In an interview, always clarify which model fits the use case.

Key components
  • Payment API: stateless HTTP, idempotency key on every POST
  • Ledger service: double-entry, append-only, source of truth
  • PSP adapter: abstracts Stripe/Adyen/Braintree behind one interface
  • Webhook worker: async delivery to merchants with retry
Interview red flags
  • Treating a payment as a single API call
  • No idempotency on the create-payment endpoint
  • Storing card numbers instead of tokens
Connects to Saga, Secrets management
Real-world: Stripe — Designing a Payment API · Stripe's payment intents model is the industry standard for auth+capture separation.
// Payment intent — the central entity in the payment lifecycle.
type PaymentIntent struct {
    ID             string         `json:"id"`
    IdempotencyKey string         `json:"idempotency_key"`
    Amount         int64          `json:"amount"`          // cents, never float
    Currency       string         `json:"currency"`
    State          PaymentState   `json:"state"`
    MerchantID     string         `json:"merchant_id"`
    TokenID        string         `json:"token_id"`        // never raw card
    PSPReference   string         `json:"psp_reference"`
    CreatedAt      time.Time      `json:"created_at"`
}

// Amount is ALWAYS integer cents. Never float64.
// $19.99 → 1999 cents. ¥1000 → 1000 (zero-decimal currency).
// This avoids floating-point rounding errors that lose/gain cents.

func CreatePaymentIntent(ctx context.Context, req CreatePaymentReq) (*PaymentIntent, error) {
    // 1. Check idempotency — return existing if same key
    if existing, err := store.GetByIdempotencyKey(ctx, req.IdempotencyKey); err == nil {
        return existing, nil   // safe replay
    }
    // 2. Create intent in PENDING state
    pi := &PaymentIntent{
        ID: ulid.New(), State: StatePending,
        Amount: req.Amount, Currency: req.Currency,
    }
    // 3. Write to ledger + persist (in a transaction)
    return pi, store.Insert(ctx, pi)
}

02

Double-entry ledger

CoreCritical
Difficulty

The story

Every financial transaction creates at least two ledger entries that sum to zero: one debit, one (or more) credits. Customer pays $19.99: debit the customer account, credit the merchant $19.30, credit the platform fee account $0.69. The invariant — sum of debits equals sum of credits — is checked on every write and in nightly reconciliation. If it ever breaks, something is catastrophically wrong.

Trade-off: double-entry vs single-balance updates. Single-balance (UPDATE balance = balance - 19.99) is simpler but loses history and is vulnerable to race conditions and silent corruption. Double-entry is more writes but gives you a complete audit trail, trivial refund logic (just reverse the entries), and balance-by-replay (no single field to corrupt). Every serious payment system uses double-entry.

Design decisions
  • Amounts in integer cents — never float (0.1 + 0.2 ≠ 0.3)
  • Append-only ledger — immutable rows, soft-delete via reversals
  • Balance = SUM(credits) - SUM(debits) per account, computed not stored
Traps
  • Float/double for money — rounding errors compound
  • Mutable balance field — race conditions and silent drift
  • Deleting ledger rows — you lose the audit trail
Connects to Audit logging, Transactions
Real-world: Stripe — Accounting for developers · Square — Books: immutable double-entry at scale
// Double-entry ledger write — always in a transaction.
type LedgerEntry struct {
    TxID      string
    Account   string
    Direction string    // "debit" or "credit"
    Amount    int64     // cents
    Currency  string
}

func (l *Ledger) Transfer(ctx context.Context, entries []LedgerEntry) error {
    // Validate invariant: sum of debits = sum of credits
    var debits, credits int64
    for _, e := range entries {
        if e.Direction == "debit"  { debits += e.Amount }
        if e.Direction == "credit" { credits += e.Amount }
    }
    if debits != credits {
        return fmt.Errorf("invariant violated: %d != %d", debits, credits)
    }
    // Atomic insert — all entries or none
    return l.db.WithTx(ctx, func(tx pgx.Tx) error {
        for _, e := range entries {
            _, err := tx.Exec(ctx, `INSERT INTO ledger
                (tx_id, account, direction, amount, currency) VALUES ($1,$2,$3,$4,$5)`,
                e.TxID, e.Account, e.Direction, e.Amount, e.Currency)
            if err != nil { return err }
        }
        return nil
    })
}

// Balance: computed from ledger entries, never stored as a field.
func (l *Ledger) Balance(ctx context.Context, account string) (int64, error) {
    var bal int64
    err := l.db.QueryRow(ctx, `
        SELECT COALESCE(SUM(CASE WHEN direction='credit' THEN amount ELSE -amount END), 0)
        FROM ledger WHERE account = $1`, account).Scan(&bal)
    return bal, err
}
# Double-entry ledger — append-only, invariant-checked.
async def transfer(db, entries: list[LedgerEntry]):
    debits  = sum(e.amount for e in entries if e.direction == "debit")
    credits = sum(e.amount for e in entries if e.direction == "credit")
    assert debits == credits, "invariant violated"

    async with db.transaction():
        for e in entries:
            await db.execute("""INSERT INTO ledger
                (tx_id, account, direction, amount, currency)
                VALUES ($1,$2,$3,$4,$5)""",
                e.tx_id, e.account, e.direction, e.amount, e.currency)

# Refund: just reverse the entries, append new rows.
async def refund(db, original_tx_id: str):
    original = await db.fetch("SELECT * FROM ledger WHERE tx_id=$1", original_tx_id)
    reversed_entries = [
        e._replace(tx_id=new_tx_id,
                   direction="credit" if e.direction == "debit" else "debit")
        for e in original]
    await transfer(db, reversed_entries)
// Spring — transactional ledger write with invariant check.
@Service
public class Ledger {
    private final JdbcTemplate jdbc;

    @Transactional
    public void transfer(List<LedgerEntry> entries) {
        long debits  = entries.stream()
            .filter(e -> e.direction() == Direction.DEBIT)
            .mapToLong(LedgerEntry::amount).sum();
        long credits = entries.stream()
            .filter(e -> e.direction() == Direction.CREDIT)
            .mapToLong(LedgerEntry::amount).sum();
        if (debits != credits)
            throw new IllegalStateException("invariant violated");

        entries.forEach(e -> jdbc.update(
            "INSERT INTO ledger (tx_id,account,direction,amount,currency) VALUES (?,?,?,?,?)",
            e.txId(), e.account(), e.direction().name(), e.amount(), e.currency()));
    }
}
03

Idempotency & exactly-once processing

CoreCritical
Difficulty

The story

The client POSTs a payment with Idempotency-Key: abc. The server processes it and saves the result. The response gets lost in the network. The client retries with the same key. Without idempotency: customer gets charged twice. With idempotency: the server sees the key, returns the cached result, and never calls the PSP again. The same input always produces the same output with no additional side effects.

Trade-off: where to store idempotency keys. In the same DB transaction as the payment (strong guarantee, simpler) vs in Redis (faster lookup, but requires careful coordination). Stripe uses the DB approach — the idempotency key, the request body hash, and the response are stored atomically alongside the payment. Keys expire after 24-48 hours.

Design decisions
  • Key + request hash + response stored atomically with the payment
  • Keys expire after 24-48h — not forever
  • If in-flight (processing), return 409 Conflict, not a retry
Traps
  • Checking idempotency outside the DB transaction — race condition
  • Same key with different body → reject with 422
  • No idempotency at all — the classic double-charge
Connects to Idempotency, State machine
Real-world: Stripe — Designing robust idempotency keys · The definitive guide to the pattern.
// Idempotency middleware — check before processing, save after.
func IdempotentHandler(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        key := r.Header.Get("Idempotency-Key")
        if key == "" { http.Error(w, "missing idempotency key", 400); return }

        // Check: already processed?
        cached, err := store.GetIdempotencyResult(r.Context(), key)
        if err == nil {
            w.WriteHeader(cached.StatusCode)
            w.Write(cached.Body); return  // replay cached response
        }
        // Lock the key (prevent concurrent retries)
        if !store.LockKey(r.Context(), key) {
            http.Error(w, "request in flight", 409); return
        }
        // Process
        rec := httptest.NewRecorder()
        next.ServeHTTP(rec, r)
        // Save result atomically
        store.SaveIdempotencyResult(r.Context(), key, rec)
        w.WriteHeader(rec.Code)
        w.Write(rec.Body.Bytes())
    })
}
# Idempotency — FastAPI dependency.
async def idempotent(request: Request, db=Depends(get_db)):
    key = request.headers.get("Idempotency-Key")
    if not key: raise HTTPException(400, "missing idempotency key")

    cached = await db.fetchrow(
        "SELECT status_code, body FROM idempotency WHERE key=$1", key)
    if cached:
        return JSONResponse(json.loads(cached["body"]),
                           status_code=cached["status_code"])
    # Acquire advisory lock to prevent concurrent retries
    await db.execute("SELECT pg_advisory_xact_lock(hashtext($1))", key)
    return None  # proceed to handler, save result after
// Spring AOP — idempotency around annotated methods.
@Around("@annotation(Idempotent)")
public Object checkIdempotency(ProceedingJoinPoint jp) throws Throwable {
    String key = getIdempotencyKey();  // from request header
    Optional<CachedResponse> cached = repo.findByKey(key);
    if (cached.isPresent()) return cached.get().toResponse();

    Object result = jp.proceed();   // execute handler
    repo.save(new CachedResponse(key, result));
    return result;
}
04

Payment state machine

CoreArchitecture
Difficulty

The story

A payment has explicit states and guarded transitions. You can't go from pending to settled — you must pass through authorised and captured. The state machine makes illegal transitions impossible at the code level, not just by convention. Every state transition is logged, and the transition function is the single place where business rules live.

Trade-off: enum + switch vs state machine library. For a payment system with 7-8 states, an explicit enum with a transition function is simpler and easier to test than a full state machine framework. The key rule: the transition function takes (current_state, event) → (new_state, side_effects). If the transition is invalid, it throws — never silently ignores.

Design decisions
  • State stored in DB, transitions happen in a transaction
  • Transition function: (state, event) → new_state or error
  • Every transition emits a domain event for downstream consumers
Traps
  • String-based state with no validation of transitions
  • Allowing "backwards" transitions (settled → authorised)
  • Business logic spread across multiple services instead of one machine
Connects to Ledger, Saga, Event sourcing
Real-world: GoCardless — Statesman: a state machine approach · How GoCardless models payment lifecycles.
// Payment state machine — explicit transitions, impossible to skip.
type PaymentState string
const (
    Pending    PaymentState = "pending"
    Authorised PaymentState = "authorised"
    Captured   PaymentState = "captured"
    Settled    PaymentState = "settled"
    Failed     PaymentState = "failed"
    Refunded   PaymentState = "refunded"
)

// Allowed transitions — the source of truth.
var transitions = map[PaymentState][]PaymentState{
    Pending:    {Authorised, Failed},
    Authorised: {Captured, Failed},
    Captured:   {Settled, Refunded},
    Settled:    {Refunded},
}

func Transition(current, next PaymentState) error {
    for _, allowed := range transitions[current] {
        if allowed == next { return nil }
    }
    return fmt.Errorf("illegal transition %s → %s", current, next)
}
# State machine — dict of allowed transitions.
TRANSITIONS = {
    "pending":    ["authorised", "failed"],
    "authorised": ["captured", "failed", "cancelled"],
    "captured":   ["settled", "refunded"],
    "settled":    ["refunded"],
}

def transition(current: str, target: str) -> str:
    if target not in TRANSITIONS.get(current, []):
        raise ValueError(f"illegal: {current} → {target}")
    return target

# In the handler — atomic transition + ledger write.
async def capture_payment(db, payment_id: str):
    async with db.transaction():
        pi = await db.fetchrow(
            "SELECT * FROM payments WHERE id=$1 FOR UPDATE", payment_id)
        new_state = transition(pi["state"], "captured")
        await db.execute("UPDATE payments SET state=$1 WHERE id=$2",
                        new_state, payment_id)
        await ledger.record_capture(pi)
// Java enum with allowed transitions built in.
public enum PaymentState {
    PENDING("authorised", "failed"),
    AUTHORISED("captured", "failed", "cancelled"),
    CAPTURED("settled", "refunded"),
    SETTLED("refunded"),
    FAILED(), CANCELLED(), REFUNDED();

    private final Set<String> allowed;
    PaymentState(String... next) { allowed = Set.of(next); }

    public PaymentState transitionTo(PaymentState target) {
        if (!allowed.contains(target.name().toLowerCase()))
            throw new IllegalStateException(this + " → " + target);
        return target;
    }
}

Saga: multi-party payment flow

CoreDistributed
Difficulty

The story

A checkout touches multiple services: reserve inventory, charge payment, trigger shipping. If payment fails after inventory is reserved, you must compensate — release the reservation. A saga is a sequence of local transactions where each step has a compensating action. If step N fails, you run compensations for steps N-1 through 1 in reverse order.

Trade-off: orchestrator vs choreography. For payments, orchestrator wins. A central saga coordinator (Temporal, Cadence, a custom state machine) knows exactly which step you're on, can retry failed steps, and gives you one place to see the entire flow. Choreography (events flying between services) is more decoupled but much harder to debug when money is stuck in limbo. When an interviewer asks, say orchestrator and explain why: observability, retry logic, and "show me where the money is right now."

Design decisions
  • Orchestrator pattern (Temporal/Cadence) for the checkout flow
  • Every step has a compensating action defined upfront
  • Saga state persisted — survives service restarts
Traps
  • Choreography for payment flows — impossible to debug
  • No compensation defined — money gets stuck
  • Compensations that can themselves fail — need idempotent retries
Connects to Saga pattern, Idempotency, State machine
Real-world: Uber — Cadence: fault-tolerant orchestration · How Uber orchestrates multi-step payment and ride flows.
// Temporal workflow — the saga orchestrator.
func CheckoutWorkflow(ctx workflow.Context, order Order) error {
    // Step 1: Reserve inventory
    err := workflow.ExecuteActivity(ctx, ReserveInventory, order).Get(ctx, nil)
    if err != nil { return err }  // nothing to compensate yet

    // Step 2: Charge payment
    err = workflow.ExecuteActivity(ctx, ChargePayment, order).Get(ctx, nil)
    if err != nil {
        // Compensate step 1
        _ = workflow.ExecuteActivity(ctx, ReleaseInventory, order).Get(ctx, nil)
        return err
    }

    // Step 3: Trigger shipping
    err = workflow.ExecuteActivity(ctx, TriggerShipping, order).Get(ctx, nil)
    if err != nil {
        // Compensate steps 2, 1 in reverse
        _ = workflow.ExecuteActivity(ctx, RefundPayment, order).Get(ctx, nil)
        _ = workflow.ExecuteActivity(ctx, ReleaseInventory, order).Get(ctx, nil)
        return err
    }
    return nil
}
# Saga orchestrator — simple sequential with compensations.
class CheckoutSaga:
    def __init__(self):
        self.compensations: list = []

    async def execute(self, order):
        try:
            await inventory.reserve(order)
            self.compensations.append(
                lambda: inventory.release(order))

            await payment.charge(order)
            self.compensations.append(
                lambda: payment.refund(order))

            await shipping.trigger(order)
        except Exception:
            # Run compensations in reverse
            for comp in reversed(self.compensations):
                await comp()
            raise
// Spring — saga orchestrator with compensation list.
public Order checkout(Order order) {
    Deque<Runnable> compensations = new ArrayDeque<>();
    try {
        inventory.reserve(order);
        compensations.push(() -> inventory.release(order));

        payment.charge(order);
        compensations.push(() -> payment.refund(order));

        shipping.trigger(order);
        return order;
    } catch (Exception e) {
        compensations.forEach(Runnable::run);
        throw e;
    }
}

Tokenisation & PCI compliance

SecurityCritical
Difficulty

The story

The card number never touches your server. The browser sends it directly to Stripe/Adyen via their client-side SDK, which returns a token. Your server only ever sees tok_abc123. This keeps you out of PCI DSS Level 1 scope (which requires on-site audits, penetration testing, and hundreds of thousands in compliance costs) and into SAQ-A (a self-assessment questionnaire).

Trade-off: hosted payment page vs embedded elements. A hosted page (redirect to Stripe Checkout) has zero PCI scope but less control over UX. Embedded elements (Stripe Elements, Adyen Drop-in) give you custom UX with minimal PCI scope. Self-hosted card forms put you in full PCI scope — almost never worth it.

Design decisions
  • Client-side tokenisation via PSP SDK (Stripe Elements, Adyen Drop-in)
  • Store only tokens, never raw PANs
  • Network tokens for higher auth rates on recurring payments
Traps
  • Card numbers in your DB, logs, or error messages
  • Logging full request bodies that include card data
  • Self-hosted card forms without full PCI compliance
Connects to Encryption, Secrets
Real-world: Stripe — Security at Stripe · Adyen — Network tokenisation

Reconciliation & settlement

OpsCritical
Difficulty

The story

Your ledger says you captured $107.49. The bank's settlement file says $77.49 arrived. That $30 gap is either a timing issue (capture succeeded but settlement hasn't landed yet) or a real problem (the capture silently failed). Reconciliation compares your ledger with the PSP's settlement report, finds mismatches, and flags them for resolution.

Trade-off: real-time recon vs nightly batch. Nightly batch is standard — PSPs provide settlement files on T+1 or T+2 cadence. Real-time reconciliation (webhook-driven) catches issues faster but is more complex and requires handling out-of-order events. Most companies start with nightly and add real-time alerts for high-value transactions.

Design decisions
  • Nightly batch job: download PSP settlement file, diff against ledger
  • Three buckets: matched, unmatched-ours, unmatched-theirs
  • Auto-retry pending captures, alert on true mismatches
Traps
  • No reconciliation at all — you won't know money is missing
  • Comparing totals only, not line-by-line
  • Ignoring small discrepancies — they compound
Connects to Ledger, Incident response
Real-world: Airbnb — Scaling the payment platform
// Nightly reconciliation — compare ledger vs PSP settlement.
func Reconcile(ctx context.Context, date time.Time) *ReconReport {
    ours := ledger.CapturedForDate(ctx, date)     // map[psp_ref]amount
    theirs := psp.DownloadSettlement(ctx, date)  // map[psp_ref]amount

    report := &ReconReport{}
    for ref, amt := range ours {
        if settled, ok := theirs[ref]; ok && settled == amt {
            report.Matched++
        } else {
            report.Unmatched = append(report.Unmatched, ref)
        }
    }
    return report
}
# Reconciliation: download PSP file, diff against ledger.
async def reconcile(date: date):
    ours = await ledger.captured_for_date(date)   # {psp_ref: amount}
    theirs = await psp.download_settlement(date)

    matched, unmatched = [], []
    for ref, amt in ours.items():
        if theirs.get(ref) == amt:
            matched.append(ref)
        else:
            unmatched.append(ref)
    if unmatched:
        await alert.fire(f"Recon mismatch: {len(unmatched)} items")
// Spring @Scheduled nightly recon job.
@Scheduled(cron = "0 0 6 * * *")   // 6am daily
public void reconcile() {
    var date = LocalDate.now().minusDays(1);   // T+1
    var ours = ledger.capturedForDate(date);
    var theirs = psp.downloadSettlement(date);

    var unmatched = ours.entrySet().stream()
        .filter(e -> !e.getValue().equals(theirs.get(e.getKey())))
        .toList();
    if (!unmatched.isEmpty())
        alertService.fire("Recon mismatch: " + unmatched.size());
}
08

Webhook delivery & merchant notification

IntegrationPattern
Difficulty

The story

After a payment state change, you notify the merchant via webhook. The delivery pipeline: event → message queue → worker → HTTP POST to merchant's URL. If the merchant returns non-2xx, retry with exponential backoff (5s, 30s, 5m, 30m, 2h, 24h). After 72 hours of failures, dead-letter and alert. Every webhook is HMAC-signed so the merchant can verify it's genuinely from you, not a spoofed request.

Trade-off: at-least-once vs exactly-once delivery. Webhooks are at-least-once — you might deliver the same event twice (network glitch, timeout misread). The merchant must be idempotent using the event_id as a dedup key. This is a contract, not a suggestion — document it prominently in your API docs.

Design decisions
  • HMAC-SHA256 signature on every webhook
  • Exponential backoff with jitter, dead-letter after 72h
  • Event ID for merchant-side dedup (at-least-once delivery)
Traps
  • No signature — anyone can spoof webhook calls
  • No retry — merchant misses events silently
  • Assuming exactly-once — always design for at-least-once

// Webhook sender — HMAC-signed, retried, idempotent event_id.
func SendWebhook(ctx context.Context, endpoint string, event Event) error {
    body, _ := json.Marshal(event)
    ts := time.Now().Unix()
    mac := hmac.New(sha256.New, []byte(secret))
    mac.Write([]byte(fmt.Sprintf("%d.%s", ts, body)))
    sig := hex.EncodeToString(mac.Sum(nil))

    req, _ := http.NewRequest("POST", endpoint, bytes.NewReader(body))
    req.Header.Set("Webhook-Signature", fmt.Sprintf("t=%d,v1=%s", ts, sig))
    req.Header.Set("Webhook-ID", event.ID)  // dedup key

    resp, err := httpClient.Do(req)
    if err != nil || resp.StatusCode >= 300 {
        return fmt.Errorf("delivery failed, will retry")
    }
    return nil
}

import hmac, hashlib, time, httpx

async def send_webhook(url: str, event: dict, secret: str):
    body = json.dumps(event)
    ts = int(time.time())
    sig = hmac.new(secret.encode(), f"{ts}.{body}".encode(),
                    hashlib.sha256).hexdigest()

    resp = await httpx.AsyncClient().post(url,
        content=body,
        headers={
            "Webhook-Signature": f"t={ts},v1={sig}",
            "Webhook-ID": event["id"],
        }, timeout=5)
    resp.raise_for_status()
