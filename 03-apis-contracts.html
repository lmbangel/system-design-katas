Tier two · Pillar 03

The contract is the product.

Once an API ships, your customers' code is welded to it. This page is about choosing a protocol, evolving it without breaking anyone, and the auth, rate-limit, and idempotency machinery that makes a real service.

Concepts10
Reading time40 min
LanguagesGo · Python · TypeScript
PRINCIPLE 01

Backwards-compat or bust.

You can add. You can deprecate. You cannot quietly remove. Every breaking change is a customer migration project — yours and theirs.

PRINCIPLE 02

Errors are an API.

Status codes, error bodies, retry-after hints — these are part of the contract. Sloppy errors create sloppy clients.

PRINCIPLE 03

Validate at the edge.

Schemas, types, and contract tests catch drift before it becomes someone's incident. Trust nothing inside, then trust everything inside.

PRINCIPLE 04

Idempotency > semantics.

"Exactly once" is a lie at the protocol level. Idempotency keys make retries safe, and that's what actually ships.

01

REST vs gRPC vs GraphQL

Core Choice
Difficulty

The story

Three families dominate. REST is request/response over JSON — every language, every tool, every browser speaks it. It's verbose and chatty (multiple round-trips for related data), the schema is whatever your docs claim, but you can debug with curl, cache at the CDN, and onboard a third-party in an afternoon.

gRPC binds protobuf-defined services to HTTP/2 with bidirectional streaming, generated clients, and tiny binary payloads multiplexed over one connection. Brilliant inside a service mesh, painful from a browser. GraphQL takes one client query and lets the server resolver fan out to whichever data sources it needs — perfect for diverse mobile/web frontends — but it pushes complexity to the server and quietly produces N+1 queries unless you wire DataLoader-style batching.

Use when
  • REST: public APIs, third-party integrations, browser-facing
  • gRPC: internal service-to-service, tight latency, polyglot codegen
  • GraphQL: client-shaped queries across many entity types
Avoid when
  • gRPC for public APIs without a REST gateway
  • GraphQL without strict depth/complexity limits
  • REST when you really need streaming (use SSE or gRPC)
Connects to Versioning, Schema evolution, Gateway

02

API versioning

Core Practical
Difficulty

The story

Once you ship a public API, you've signed a contract. The question isn't whether to version — it's where to put the version. URL path (/v2/orders) is the most common because it's obvious, browser-debuggable, and cleanly separates routing. Custom header (Stripe's API-Version: 2024-08-15) keeps URLs clean and lets you ship many small changes — but only if you commit to the rolling-date approach.

The senior move isn't picking the cleverest scheme — it's committing to backwards compatibility within a major version. v2 should never break v1; you ship v3 instead. Sunset old versions on a written calendar (12+ months) and tell customers exactly when. Header-based works only if your team has the discipline to never silently mutate the schema.

Use when
  • URL path: most APIs, especially public ones
  • Header: many small changes, sophisticated SDKs
  • Major version bumps: only for breaking changes
Avoid
  • Mixing schemes — pick one and stick to it
  • Removing fields without a deprecation window
  • Bumping versions for additive changes
Connects to Schema evolution, Error model
// URL-path versioning — the boring, correct default.
func routes(svc *OrderService) http.Handler {
    r := chi.NewRouter()

    // v1 — the original. Maintained for old SDKs.
    r.Route("/v1", func(r chi.Router) {
        r.Get("/orders/{id}", svc.getOrderV1)
    })

    // v2 — adds new fields, renames status values.
    // Old clients keep using v1 until they migrate.
    r.Route("/v2", func(r chi.Router) {
        r.Get("/orders/{id}", svc.getOrderV2)
    })

    // Deprecation header — every v1 response carries this
    r.Use(func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            if strings.HasPrefix(r.URL.Path, "/v1/") {
                w.Header().Set("Sunset", "Wed, 01 Oct 2026 00:00:00 GMT")
                w.Header().Set("Deprecation", "true")
                w.Header().Set("Link",
                    `</v2/orders>; rel="successor-version"`)
            }
            next.ServeHTTP(w, r)
        })
    })
    return r
}
# Header-based versioning — Stripe-style rolling dates.
from fastapi import FastAPI, Header, HTTPException

app = FastAPI()

# All released versions, oldest first. Each transformer rewrites
# the response from the *next* version back to its own shape.
VERSIONS = [
    ("2024-01-15", lambda o: {**o, "status": o["status"].lower()}),
    ("2024-08-15", lambda o: {k: v for k, v in o.items() if k != "audit"}),
    ("2025-02-01", lambda o: o),                     # current
]

@app.get("/orders/{order_id}")
async def get_order(
    order_id: str,
    api_version: str = Header("2025-02-01", alias="API-Version"),
):
    # Reject unknown / future-dated versions early
    known = [v for v, _ in VERSIONS]
    if api_version not in known:
        raise HTTPException(400, f"unknown API-Version: {api_version}")

    order = await load_order(order_id)             # latest shape

    # Walk transformers backwards from latest to requested
    for version, transform in reversed(VERSIONS):
        if version <= api_version:
            break
        order = transform(order)
    return order

03

Schema evolution

Core Discipline
Difficulty

The story

Once a schema is published, it splits into backward compatible changes (new readers can still parse old data) and forward compatible changes (old readers can still parse new data). The first lets you upgrade producers without rolling out consumers; the second lets you do the reverse. Both at once is what people mean by "non-breaking."

Protobuf and Avro were designed for evolution: tagged fields, default values, and never reusing tag numbers. Add a field with a new tag, mark old ones reserved, and old binaries shrug at the unknown bytes. JSON has no such discipline — you have to enforce it yourself with a schema registry, JSON Schema validators, or contract tests in CI. The senior move: codify "no rename, no remove, no retype" as a CI check before the change can merge.

Use when
  • Protobuf/Avro for inter-service contracts
  • JSON Schema for REST/JSON APIs in CI
  • Contract tests that fail PRs on breaking diffs
Avoid
  • Reusing field numbers in protobuf — always reserve
  • Tightening validation on existing fields silently
  • "It's just a rename" — it isn't, ever
Connects to Versioning, CDC
// .proto evolution — what's safe, what isn't.
// orders/v1/order.proto — original
message Order {
    string id           = 1;
    int64  total_cents  = 2;
    string status       = 3;
    string user_id      = 4;
}

// orders/v1/order.proto — evolved (still v1, no break)
message Order {
    string id           = 1;
    int64  total_cents  = 2;
    string status       = 3;
    string user_id      = 4;

    // ✓ NEW — old clients ignore unknown fields
    string currency     = 5;
    repeated string tags = 6;

    // ✗ Wanted to remove `user_id`? Don't. Reserve it forever.
    reserved 99, 100;                    // numbers used + retired
    reserved "old_field_name";          // names too
}

04

Pagination · cursor vs offset

Core Practical
Difficulty

The story

Offset pagination (?page=3&size=20) makes the database walk every row from the start. Page 50 forces Postgres to read 1,000 rows just to throw the first 980 away. Worse, if a row is inserted while the user paginates, they'll see a duplicate or skip a row — the offset shifts under them.

Cursor pagination encodes "the last row I saw" in an opaque token (typically base64-encoded (sort_value, id)). The server re-issues a WHERE (sort, id) > (last_sort, last_id) query that uses the index directly — O(log N) regardless of depth, stable under inserts. The cost: no random access ("jump to page 50"), and you need a stable, indexed sort key with a tie-breaker (timestamp + id).

Cursor when
  • Feeds, infinite scroll, large result sets
  • Paginating mutating data (orders, events, messages)
  • Anything beyond a few thousand rows total
Offset when
  • Tiny, finite result sets (admin tables < 1k rows)
  • Users genuinely need to jump to page N
  • You can index the sort and tolerate small inconsistencies
Connects to Indexes, Query plans
// Cursor pagination — opaque token holds (created_at, id).
type Cursor struct {
    CreatedAt time.Time `json:"t"`
    ID        int64     `json:"i"`
}

func encodeCursor(c Cursor) string {
    b, _ := json.Marshal(c)
    return base64.URLEncoding.EncodeToString(b)
}

func (s *Service) ListOrders(ctx context.Context,
    after string, limit int) ([]Order, string, error) {

    var cur Cursor
    if after != "" {
        b, _ := base64.URLEncoding.DecodeString(after)
        json.Unmarshal(b, &cur)
    }
    if limit <= 0 || limit > 100 { limit = 25 }   // always cap

    // Index on (created_at, id) — tuple comparison is index-friendly
    rows, err := s.db.QueryContext(ctx, `
        SELECT id, created_at, total
          FROM orders
         WHERE (created_at, id) > ($1, $2)
         ORDER BY created_at, id
         LIMIT $3
    `, cur.CreatedAt, cur.ID, limit+1)             // +1 to know if there's more
    if err != nil { return nil, "", err }

    orders, _ := scanAll(rows)
    var next string
    if len(orders) > limit {
        last := orders[limit-1]
        next = encodeCursor(Cursor{CreatedAt: last.CreatedAt, ID: last.ID})
        orders = orders[:limit]
    }
    return orders, next, nil
}
# FastAPI cursor pagination — opaque, signed (so clients can't tamper).
import base64, json, hmac, hashlib, os
from fastapi import FastAPI, HTTPException, Query

SECRET = os.environ["CURSOR_SECRET"].encode()

def encode_cursor(payload: dict) -> str:
    body = json.dumps(payload, separators=(",", ":")).encode()
    sig  = hmac.new(SECRET, body, hashlib.sha256).digest()[:8]
    return base64.urlsafe_b64encode(body + sig).decode().rstrip("=")

def decode_cursor(tok: str) -> dict:
    raw = base64.urlsafe_b64decode(tok + "==")
    body, sig = raw[:-8], raw[-8:]
    good = hmac.compare_digest(
        sig, hmac.new(SECRET, body, hashlib.sha256).digest()[:8])
    if not good:
        raise HTTPException(400, "invalid cursor")
    return json.loads(body)

@app.get("/v1/orders")
async def list_orders(
    after: str | None = None,
    limit: int = Query(25, le=100),
):
    cur = decode_cursor(after) if after else {"t": "1970-01-01", "i": 0}

    rows = await db.fetch("""
        SELECT id, created_at, total FROM orders
         WHERE (created_at, id) > ($1, $2)
         ORDER BY created_at, id
         LIMIT $3
    """, cur["t"], cur["i"], limit + 1)

    items, next_cur = rows[:limit], None
    if len(rows) > limit:
        last = items[-1]
        next_cur = encode_cursor({"t": last["created_at"].isoformat(),
                                   "i": last["id"]})
    return {"items": items, "next": next_cur}

export interface Page<T> { items: T[]; next: string | null; }

export class OrderRepo {
    constructor(private readonly db: Pool) {}

    async listAfter(afterTs: Date, afterId: number, limit: number): Promise<Page<Order>> {
        const { rows } = await this.db.query<Order>(`
            SELECT id, created_at AS "createdAt", total
              FROM orders
             WHERE (created_at, id) > ($1, $2)
             ORDER BY created_at, id
             LIMIT $3
        `, [afterTs, afterId, limit + 1]);

        if (rows.length <= limit)
            return { items: rows, next: null };

        const page = rows.slice(0, limit);
        const last = page[page.length - 1];
        const next = CursorCodec.encode(last.createdAt, last.id);
        return { items: page, next };
    }
}
05

Error model design

Core Practical
Difficulty

The story

Error responses are the most-tested code path in your API — every client writes if err first. A good error tells the client: what kind (status code), what specifically (machine-readable code), why for a human (detail message), and how to find it again (trace id). The IETF formalised this as RFC 7807 Problem Details — same shape across every endpoint, parseable, extensible.

The mistakes to avoid: leaking stack traces (security), embedding SQL or internal IDs (information disclosure), changing error codes between versions (breaks alerts), and using 200 OK with {"success": false} in the body. HTTP status codes exist for a reason — clients and proxies rely on them. Reserve 4xx for client errors, 5xx for server errors, and never blur the line.

Use when
  • RFC 7807 problem+json on every error response
  • Stable machine-readable code that survives version bumps
  • trace_id in every response — request and error
Avoid
  • 200 OK with error in body — breaks every retry policy
  • Stack traces or DB internals in detail
  • Made-up status codes (418 for love, 420 for blaze, etc.)
Connects to Circuit Breaker, Rate limiting, Tracing
// One Problem type, used by every error path.
type Problem struct {
    Type     string `json:"type"`           // canonical URL
    Title    string `json:"title"`          // short, fixed
    Status   int    `json:"status"`         // HTTP code
    Detail   string `json:"detail,omitempty"`
    Instance string `json:"instance,omitempty"` // what URI
    Code     string `json:"code"`           // stable machine code
    TraceID  string `json:"trace_id,omitempty"`
}

func writeProblem(w http.ResponseWriter, r *http.Request, p Problem) {
    p.Instance = r.URL.Path
    p.TraceID = trace.SpanContextFromContext(r.Context()).TraceID().String()
    w.Header().Set("Content-Type", "application/problem+json")
    w.WriteHeader(p.Status)
    json.NewEncoder(w).Encode(p)
}

06

Rate limiting · token bucket

Core Defense
Difficulty

The story

Rate limits are how you tell abusive callers "no" without taking down the rest of your service. Token bucket is the most common algorithm: each user has a bucket that refills at R tokens/sec up to a max C. Each request takes one token; out of tokens, get 429. Generous on bursts (up to capacity), simple to reason about, easy to share across nodes via Redis.

Other algorithms exist for different shapes: leaky bucket shapes traffic to a constant outflow (good for protecting fragile downstreams), fixed window ("100 calls per minute") is trivial but lets users do 200 across the minute boundary, sliding window fixes that. Always return 429 Too Many Requests with Retry-After, plus X-RateLimit-Limit and X-RateLimit-Remaining on every response so well-behaved clients can self-throttle.

Use when
  • Token bucket: most public APIs (Stripe, GitHub style)
  • Sliding window: per-tenant quotas with hard limits
  • Leaky bucket: protecting fragile downstreams
Avoid
  • Fixed window for hard SLAs — edge bursts violate them
  • Per-IP only — NAT and Cloudflare break it
  • Silently dropping — always return 429 + Retry-After
Connects to Circuit Breaker, Errors
// Token bucket — Redis-backed for distributed services.
// Lua script ensures atomic check + decrement.
const tokenBucketLua = `
local key       = KEYS[1]
local capacity  = tonumber(ARGV[1])
local refill    = tonumber(ARGV[2])     -- tokens / sec
local now       = tonumber(ARGV[3])     -- ms
local cost      = tonumber(ARGV[4])

local b = redis.call('HMGET', key, 'tokens', 'ts')
local tokens = tonumber(b[1]) or capacity
local ts     = tonumber(b[2]) or now

local elapsed = math.max(0, now - ts) / 1000
tokens = math.min(capacity, tokens + elapsed * refill)

if tokens < cost then
  redis.call('HMSET', key, 'tokens', tokens, 'ts', now)
  redis.call('PEXPIRE', key, 60000)
  return {0, math.ceil((cost - tokens) / refill * 1000)}  -- retry ms
end

tokens = tokens - cost
redis.call('HMSET', key, 'tokens', tokens, 'ts', now)
redis.call('PEXPIRE', key, 60000)
return {1, 0}
`

func RateLimit(capacity, refillPerSec int) func(http.Handler) http.Handler {
    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            key := "rl:" + tenantID(r)
            res, _ := redis.Eval(tokenBucketLua, []string{key},
                capacity, refillPerSec, time.Now().UnixMilli(), 1).Result()
            arr := res.([]interface{})
            if arr[0].(int64) == 0 {
                w.Header().Set("Retry-After",
                    strconv.FormatInt(arr[1].(int64)/1000, 10))
                http.Error(w, "rate limited", 429)
                return
            }
            next.ServeHTTP(w, r)
        })
    }
}

def rate_limit(limit: int, window_s: int):
    async def dep(req: Request):
        tenant = req.state.tenant_id
        key    = f"rl:{tenant}"
        now_ms = int(time.time() * 1000)
        cutoff = now_ms - window_s * 1000

        # Atomic: drop expired, count current, add new request
        async with r.pipeline() as p:
            p.zremrangebyscore(key, 0, cutoff)
            p.zcard(key)
            p.zadd(key, {f"{now_ms}-{req.state.req_id}": now_ms})
            p.expire(key, window_s + 1)
            _, used, _, _ = await p.execute()

        remaining = max(0, limit - used - 1)
        req.state.rl_remaining = remaining             # middleware adds headers

        if used >= limit:
            raise HTTPException(429, headers={"Retry-After": str(window_s)})

    return dep

Authentication · the JWT flow

Core Security
Difficulty

The story

Sessions: server stores a random opaque ID, browser sends it as an httpOnly cookie. Easy to revoke (delete the row), but you need a sticky session store and CSRF protection. Best for traditional web apps. JWTs: signed token containing claims (subject, expiry, scopes). Stateless — any service with the public key can verify it without phoning home. Pitfall: JWTs are hard to revoke.

Mitigation is the dual-token pattern shown above: a short-lived access token (5–15 min) for API calls, a long-lived refresh token (days/weeks) used only against the auth server to get new access tokens. When you need to revoke, the refresh token is in your DB and easy to delete; existing access tokens expire on their own. OAuth 2.1 standardises the flows for third-party access; if you're doing "Sign in with Google", you're doing OAuth + OIDC. Use a vetted library — never roll your own.

Use when
  • Sessions: same-origin web apps
  • JWT: service-to-service or single-page apps with refresh
  • OAuth: third-party access, social login, delegated auth
Avoid
  • Long-lived JWTs without revocation
  • Tokens in localStorage (XSS = total compromise)
  • Hand-rolled crypto — use jose / passport / Spring Security
Connects to Authorization, Security

func JWTAuth(jwks *jose.JSONWebKeySet) func(http.Handler) http.Handler {
    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            tok := strings.TrimPrefix(r.Header.Get("Authorization"), "Bearer ")
            if tok == "" {
                writeProblem(w, r, ErrUnauthorized); return
            }

            // Parse + verify against JWKS — refuses 'alg=none' by design
            parsed, err := jwt.ParseSigned(tok,
                []jose.SignatureAlgorithm{jose.RS256, jose.ES256})
            if err != nil {
                writeProblem(w, r, ErrUnauthorized); return
            }

            var c Claims
            if err := parsed.Claims(jwks, &c); err != nil {
                writeProblem(w, r, ErrUnauthorized); return
            }
            // Validate exp / nbf / iss / aud — never skip!
            if err := c.Validate(jwt.Expected{
                Issuer: "https://auth.x.com", Audience: jwt.Audience{"api"},
                Time: time.Now(),
            }); err != nil {
                writeProblem(w, r, ErrUnauthorized); return
            }

            ctx := context.WithValue(r.Context(), claimsKey, &c)
            next.ServeHTTP(w, r.WithContext(ctx))
        })
    }
}

Authorization · RBAC vs ABAC

Core Security
Difficulty

The story

Authentication proves who you are. Authorization decides what you can do. RBAC assigns users to roles and roles to permissions. It's a graph: alice → admin → {read:*, write:*}. Easy to audit, easy to onboard, but at scale you get the role explosion problem — one role per (department × region × tenure × tier) combination.

ABAC evaluates a rule over attributes of the subject, action, resource, and environment: allow if user.dept == resource.dept and time < 18:00. Vastly more expressive — but harder to reason about ("can Alice see this row?" requires running the policy). The mature pattern: RBAC for coarse-grained roles, ABAC for row-level data rules. Centralise the decision in a policy service or library (OPA, Cedar, Casbin) so every endpoint asks the same engine — and add policy tests to your test suite.

Use when
  • RBAC: small fixed set of roles, simple admin/user split
  • ABAC: multi-tenant, region or dept-scoped data
  • OPA / Cedar / Casbin to centralise the decision
Avoid
  • Permission checks scattered across handlers
  • Role explosion (50+ similar roles) — switch to ABAC
  • Trusting client-supplied user IDs — derive from token
Connects to Authentication, Security

Idempotency keys

Core Pattern
Difficulty

The story

Networks fail mid-flight. The client retries. Without protection, your service charges twice. Idempotency keys let the caller send a unique Idempotency-Key header on a write; the server stores the key alongside the result, and on any retry with the same key, returns the cached response without re-doing the work.

The state machine has three states for a key: locked (first request in flight), completed (cached response available), conflict (different request body with same key — return 422). Use Redis SETNX or a Postgres unique constraint for the lock; cache both the response and the request hash so reused keys with different bodies are rejected. Stripe's docs on this are the canonical reference — they retain keys for 24 hours.

Use when
  • Every POST/PUT that mutates money or state
  • Document the key requirement in your OpenAPI spec
  • Retain results 24h+ for legitimate retries
Avoid
  • Skipping for "internal" services — they retry too
  • Letting the same key with different body succeed silently
  • In-memory store — must survive process restarts
Connects to Saga, Errors
// Idempotency middleware — Redis-backed.
type IdemEntry struct {
    RequestHash string `json:"req"`
    Status      int    `json:"status"`
    Body        string `json:"body"`
}

func Idempotent(rdb *redis.Client) func(http.Handler) http.Handler {
    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            key := r.Header.Get("Idempotency-Key")
            if key == "" || r.Method != "POST" {
                next.ServeHTTP(w, r); return
            }

            body, _ := io.ReadAll(r.Body)
            r.Body = io.NopCloser(bytes.NewReader(body))
            hash := fmt.Sprintf("%x", sha256.Sum256(body))
            k    := "idem:" + key

            // Try to grab the lock — atomic SETNX with 1-min TTL
            locked, _ := rdb.SetNX(r.Context(), k+":lock", hash,
                60*time.Second).Result()
            if !locked {
                // Already done? Replay the cached response
                if cached, err := rdb.Get(r.Context(), k).Bytes(); err == nil {
                    var e IdemEntry
                    json.Unmarshal(cached, &e)
                    if e.RequestHash != hash {
                        writeProblem(w, r, Problem{
                            Status: 422, Code: "idempotency_key_reuse",
                        }); return
                    }
                    w.WriteHeader(e.Status); w.Write([]byte(e.Body)); return
                }
                writeProblem(w, r, Problem{Status: 409, Code: "in_progress"}); return
            }

            // Capture the response and persist it
            rec := &recorder{ResponseWriter: w, code: 200, buf: &bytes.Buffer{}}
            next.ServeHTTP(rec, r)
            e, _ := json.Marshal(IdemEntry{
                RequestHash: hash, Status: rec.code, Body: rec.buf.String(),
            })
            rdb.Set(r.Context(), k, e, 24*time.Hour)
        })
    }
}

            INSERT INTO idempotency (key, req_hash, status, body)

HTTP caching · ETag & 304

Bonus Performance
Difficulty

The story

HTTP has a complete caching protocol baked in — most APIs ignore it. Cache-Control says how long a response is fresh (max-age=60), where it can live (public for CDNs, private for browsers only), and what to do when stale (stale-while-revalidate serves the old copy while fetching a new one in the background). ETag is a content fingerprint; on the next request the client sends If-None-Match: "abc", and if the resource hasn't changed, the server returns 304 Not Modified with no body — a network round-trip but zero bandwidth.

The senior move: set Cache-Control on every response, even if it's no-store for sensitive data. Default behaviour is implementation-defined and intermediaries will surprise you. For mutable resources (a user's order), use private, max-age=0, must-revalidate with an ETag — every request still hits your server, but a 304 is ten times cheaper than a 200.

Use when
  • Static assets: long max-age + content-hash filenames
  • Public lists: short max-age + stale-while-revalidate
  • User-specific resources: ETag + must-revalidate
Avoid
  • No Cache-Control — intermediaries will guess wrong
  • Caching authenticated responses as public
  • ETag based on a timestamp that changes every read
Connects to Performance & scale, Gateway
// ETag handler — computes hash, handles If-None-Match.
func withETag(h http.HandlerFunc) http.HandlerFunc {
    return func(w http.ResponseWriter, r *http.Request) {
        rec := &recorder{ResponseWriter: w, code: 200, buf: &bytes.Buffer{}}
        h(rec, r)
        if rec.code != 200 {
            w.WriteHeader(rec.code); w.Write(rec.buf.Bytes()); return
        }

        sum  := sha256.Sum256(rec.buf.Bytes())
        etag := fmt.Sprintf(`"%x"`, sum[:8])

        if match := r.Header.Get("If-None-Match"); match == etag {
            w.Header().Set("ETag", etag)
            w.WriteHeader(http.StatusNotModified)              // 304
            return
        }
        w.Header().Set("ETag", etag)
        w.Header().Set("Cache-Control", "private, max-age=0, must-revalidate")
        w.Write(rec.buf.Bytes())
    }
}

// Public, CDN-friendly: long max-age + immutable content-hashed URL.
func staticHandler(w http.ResponseWriter, r *http.Request) {
    w.Header().Set("Cache-Control", "public, max-age=31536000, immutable")
    http.ServeFile(w, r, "./assets"+r.URL.Path)
}
