Tier three · Pillar 05

You can only fix what you can see.

A service that breaks invisibly is worse than one that breaks loudly. This page is about defining "working", instrumenting your code so the answer is always one query away, and the operational discipline that turns incidents into postmortems instead of repeats.

Concepts10
Reading time40 min
LanguagesGo · Python · Java
PRINCIPLE 01

Define "working" in numbers.

If "the API is up" means different things to different teams, the on-call has to argue before they can fix anything. SLOs make the standard a single number.

PRINCIPLE 02

Logs, metrics, traces are not interchangeable.

Metrics are aggregates, logs are events, traces are causality. Each answers a different question. Pretending one is the other is how outages last hours.

PRINCIPLE 03

Mitigate first. Root-cause second.

Roll back, fail open, drop the offending tenant. Stop the bleeding before you debug. The longest postmortems start with a heroic fix attempt.

PRINCIPLE 04

Every alert is a runbook trigger.

If an alert fires and the on-call has to think from scratch, the alert is too vague. Pages should map to a specific signal and a specific first action.

01

SLI · SLO · error budgets

Core Foundation
Difficulty

The story

An SLI is a measurable quality of service ("99.92% of requests in the last 5 min returned 2xx within 200ms"). An SLO is the target you commit to internally ("99.9% over 30 days"). An SLA is the contractual version with a customer, usually weaker than the SLO so you have headroom. The magic is the error budget: 100% — SLO. At 99.9%, you are allowed 43 minutes of downtime per month — and you should spend it. Reliability above the budget is wasted engineering you could have spent shipping.

The chart above is what mature SRE teams put on every dashboard. When the budget is fat, you ship faster, take risks, run chaos drills. When it's thin, you stop deploying anything that's not a bug fix. Burn-rate alerts page you when the budget is being consumed too fast — not just on outages, but on the trend. Page on a 14.4× burn rate sustained for 1 hour: that's enough to exhaust a 30-day budget in a day if it continues.

Use when
  • One SLI/SLO per critical user journey, not per service
  • Burn-rate alerts (multi-window: 1h × 14.4 + 6h × 6)
  • Error budget gates on deploys to risky tiers
Avoid
  • "100% uptime" — a goal, not a target. You'll always miss
  • SLOs nobody owns or reviews quarterly
  • Customer SLA tighter than internal SLO — no headroom
Connects to Golden signals, Deployments, Incidents

func SLIMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        start := time.Now()
        rec   := &recorder{ResponseWriter: w, code: 200}
        next.ServeHTTP(rec, r)
        route := routeOf(r)
        requests.WithLabelValues(route,
            fmt.Sprintf("%dxx", rec.code/100)).Inc()
        duration.WithLabelValues(route).Observe(time.Since(start).Seconds())
    })
}

    ["route", "status_class"],

DURATION = Histogram(

@app.middleware("http")
async def sli(req, call_next):
    t0 = time.perf_counter()
    res = await call_next(req)
    DURATION.labels(req.url.path).observe(time.perf_counter() - t0)
    REQUESTS.labels(req.url.path, f"{res.status_code // 100}xx").inc()
    return res

# Helper for runbook math.
def burn_rate(slo: float, observed_err_rate: float) -> float:
    """How fast is the budget being consumed, vs allowed?"""
    return observed_err_rate / (1 - slo)

# 14.4x for 1h or 6x for 6h triggers a fast-burn page.
assert burn_rate(0.999, observed_err_rate=0.0144) == 14.4

02

The four golden signals

Core Mental model
Difficulty

The story

Google's SRE book distilled decades of operations wisdom into four signals. Latency: but split it — a fast 500 hides slow 200s. Always plot p50/p95/p99 separately for success and error responses. Traffic: req/s, msgs/s, active connections. A sudden drop in traffic often means an upstream is broken; alert on that too. Errors: count explicit failures (5xx) and semantic ones (200 with the wrong body). Saturation: how full each resource is. CPU at 80% may still serve, but latency is about to hockey-stick.

Two complementary frames help: USE (Utilization, Saturation, Errors per resource — great for infrastructure) and RED (Rate, Errors, Duration per request — great for services). Together with the golden signals, they cover most dashboards you'll ever build.

Use when
  • Building your first dashboard — start with these four
  • Triage: which signal moved first tells you the category
  • Runbooks keyed to signal anomalies
Avoid
  • Dashboards with 30 graphs nobody reads
  • Averaging latency — use histograms, plot percentiles
  • Ignoring traffic drops — often the first sign of cascades
Connects to SLOs, Cardinality, Circuit breaker

    latency = prometheus.NewHistogramVec(prometheus.HistogramOpts{
        Name:    "golden_latency_seconds",
        Buckets: prometheus.DefBuckets,
    }, []string{"route", "status_class"})        // split success/error!

    traffic = prometheus.NewCounterVec(prometheus.CounterOpts{
        Name: "golden_traffic_total",
    }, []string{"route", "method"})

    errors = prometheus.NewCounterVec(prometheus.CounterOpts{
        Name: "golden_errors_total",
    }, []string{"route", "code"})

    // Saturation — gauge connection pool + goroutine count
    connPoolUsed = prometheus.NewGauge(prometheus.GaugeOpts{
        Name: "golden_db_connections_in_use",
    })
    goroutines = prometheus.NewGauge(prometheus.GaugeOpts{
        Name: "golden_goroutines",
    })
)

func GoldenSignals(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        start := time.Now()
        rec   := &recorder{ResponseWriter: w, code: 200}
        next.ServeHTTP(rec, r)
        route := routeOf(r)
        sc := fmt.Sprintf("%dxx", rec.code/100)
        latency.WithLabelValues(route, sc).Observe(time.Since(start).Seconds())
        traffic.WithLabelValues(route, r.Method).Inc()
        if rec.code >= 500 {
            errors.WithLabelValues(route, strconv.Itoa(rec.code)).Inc()
        }
        goroutines.Set(float64(runtime.NumGoroutine()))
    })
}

@app.middleware("http")
async def golden_signals(req, call_next):
    start = time.perf_counter()
    resp  = await call_next(req)
    dur   = time.perf_counter() - start

    route = getattr(req.scope.get("route"), "path", "unknown")
    sc    = f"{resp.status_code // 100}xx"

    LATENCY.labels(route, sc).observe(dur)
    TRAFFIC.labels(route, req.method).inc()
    if resp.status_code >= 500:
        ERRORS.labels(route, str(resp.status_code)).inc()
    return resp

03

Structured logging & correlation IDs

Core Practical
Difficulty

The story

Plaintext logs are human-readable until you have ten million of them. Structured logs emit JSON (or logfmt) so they're both human-readable and machine-queryable: level=error, order_id=42, code=insufficient_funds. Indexed in Loki, Elastic, or BigQuery, they let you ask "show me every charge_failed for tenant X in the last hour" without grep gymnastics.

The correlation ID — usually the W3C traceparent trace ID — threads through every service a request touches. The gateway generates it; every downstream propagates it as a header and stamps it on every log line. When something breaks, you grep one ID and see the full story across 12 services. Pair it with structured logs and a half-decent log aggregator and you've collapsed 90% of debugging into one query.

Use when
  • JSON logs everywhere, indexed by trace_id
  • Log libraries that bind fields to request context
  • Sample high-volume debug logs, always emit errors
Avoid
  • Logging PII (email, IP) without redaction rules
  • printf-style: "user " + id + " failed"
  • Logging request bodies in production (cost + security)
Connects to Distributed tracing, Cardinality
// slog (Go 1.21+) — structured, context-aware logging.
import "log/slog"

// Middleware: extract trace ID, bind to a context logger.
func LogCtx(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        traceID := trace.SpanContextFromContext(r.Context()).TraceID().String()
        logger  := slog.With(
            "trace_id", traceID,
            "method",   r.Method,
            "path",     r.URL.Path,
        )
        ctx := withLogger(r.Context(), logger)
        next.ServeHTTP(w, r.WithContext(ctx))
    })
}

04

Distributed tracing

Core Essential
Difficulty

The story

A single user click can fan out across 12 services, 3 databases, and an external API. Distributed tracing records each hop as a span (name, start, duration, attributes), nesting them into a trace (a tree of spans sharing one trace ID). The waterfall view instantly shows you where latency lives — in the example above, Stripe is 35% of total time. You'd never have spotted that from logs alone.

OpenTelemetry is the standard. It propagates context via the traceparent header (W3C format), auto-instruments HTTP clients and DB drivers, and exports spans to Jaeger, Tempo, or any OTel-compatible backend. The key discipline is sampling: tracing every request is expensive. Head-based sampling (decide at the edge) keeps cost linear; tail-based sampling (keep slow/error traces, drop fast ones) is gold but requires a collector pipeline.

Use when
  • OpenTelemetry SDK everywhere — auto-instrumentation first
  • Tail-based sampling to keep interesting traces
  • Link trace IDs to logs and metrics for full correlation
Avoid
  • 100% sampling in production — costs explode
  • Custom propagation headers — use W3C traceparent
  • Ignoring async spans (queues, cron) — break the waterfall
Connects to Structured logging, Cardinality
// OpenTelemetry: auto-instrument HTTP + a custom span for business logic.
import (
    "go.opentelemetry.io/otel"
    "go.opentelemetry.io/otel/exporters/otlp/otlptrace/otlptracehttp"
    "go.opentelemetry.io/otel/sdk/trace"
    "go.opentelemetry.io/contrib/instrumentation/net/http/otelhttp"
)

func initTracer() func() {
    exp, _ := otlptracehttp.New(context.Background())
    tp := trace.NewTracerProvider(
        trace.WithBatcher(exp),
        trace.WithSampler(trace.TraceIDRatioBased(0.1)),     // 10%
    )
    otel.SetTracerProvider(tp)
    return func() { tp.Shutdown(context.Background()) }
}

// Wrap your mux — auto-creates spans for each handler.
handler := otelhttp.NewHandler(router, "api")

// Custom span for business logic
func (s *Service) chargeOrder(ctx context.Context, o Order) error {
    ctx, span := otel.Tracer("orders").Start(ctx, "charge_order")
    defer span.End()
    span.SetAttributes(attribute.Int64("order.id", o.ID))
    return s.pay.Charge(ctx, o)
}

        } finally {
            span.end();
        }
    }
}
05

Metrics cardinality

Core Pitfall
Difficulty

The story

Every unique combination of label values creates a new time series stored independently. http_requests{route, method, status_class} with 15 routes × 4 methods × 5 status classes = 300 series — Prometheus shrugs. Add user_id and you've just told it to allocate one series per user. At scale, that's tens of millions of series, scrape timeouts, and the dreaded "metrics cardinality bomb" Slack message from your platform team.

The rule: labels are dimensions you'll group by, not identifiers. Anything with high uniqueness — user IDs, request IDs, email addresses, full URLs with query strings — belongs in logs and traces, not metric labels. If you really need to slice by tenant, cap to your top-N tenants and bucket the rest as other. Use Prometheus label limits (--storage.tsdb.max-cardinality-per-metric) and OTel views to enforce this at ingest.

Use when
  • Bounded label sets — routes, methods, status classes
  • Top-N tenants + other for the long tail
  • OTel views to drop or aggregate high-card labels
Avoid
  • User IDs, request IDs, emails, full URLs as labels
  • Stack traces or error messages — use logs
  • Untemplated routes — /orders/42 not /orders/{id}
Connects to Golden signals, Logging, Tracing
// Bounded labels — route templates, status class, top-N tenants.
var topTenants = map[string]bool{
    "acme": true, "globex": true, "initech": true,
}

func tenantLabel(id string) string {
    if topTenants[id] {
        return id
    }
    return "other"                                  // the long tail
}

// Micrometer: tag normalisation + cardinality limits.

@Configuration
public class CardinalityConfig {

    // Cap unique tag values per meter — drop overflow into "_other_"
    @Bean
    public MeterFilter limitTenants() {
        return MeterFilter.maximumAllowableTags(
            "http.server.requests", "tenant", 100,
            MeterFilter.deny());
    }

    // Use registered URI templates, not raw paths
    @Bean
    public WebMvcTagsContributor tenantTag() {
        return new WebMvcTagsContributor() {
            @Override
            public Iterable<Tag> getTags(HttpServletRequest req,
                                          HttpServletResponse res,
                                          Object handler, Throwable ex) {
                String tenant = (String) req.getAttribute("tenantId");
                return List.of(Tag.of("tenant", topOrOther(tenant)));
            }
            @Override
            public Iterable<Tag> getLongRequestTags(
                HttpServletRequest r, Object h) { return List.of(); }
        };
    }

    private static final Set<String> TOP =
        Set.of("acme", "globex", "initech");

    private static String topOrOther(String t) {
        return t != null && TOP.contains(t) ? t : "other";
    }
}
06

Graceful degradation

Core Resilience
Difficulty

The story

When a non-critical service breaks, the wrong answer is to take down the whole product. Graceful degradation means designing the UI and API so that secondary features can disappear, return cached data, or render placeholders while the core path keeps working. A product page should still show price and "buy now" even if the recommendations service is down — the customer's flow doesn't depend on knowing what other people bought.

Implement degradation in two layers. First, circuit breakers and timeouts on every cross-service call so a slow dependency doesn't cascade. Second, feature flags or tiered modes the on-call can flip during an incident: recommendations=off, chat=read-only, search=cached-only. The mature pattern is to define levels (full → degraded → minimal) and rehearse the transitions in game days.

Use when
  • Identify the critical path; everything else is droppable
  • Cached fallbacks for read-mostly data
  • Feature flags wired into UI components
Avoid
  • Showing partial pages with broken JS spinners
  • Critical path depending on optional services
  • Untested degradation modes (do game days!)
Connects to Circuit breaker, Load shedding
// Graceful degradation: feature flags + bounded fallbacks.
type FeatureFlags struct {
    RecommendationsEnabled atomic.Bool
    ReviewsEnabled         atomic.Bool
    ChatEnabled            atomic.Bool
}

type ProductPage struct {
    Product         Product           `json:"product"`
    Price           Price             `json:"price"`
    Recommendations []Product         `json:"recommendations,omitempty"`
    Reviews         *ReviewSummary    `json:"reviews,omitempty"`
    DegradedFeatures []string          `json:"degraded,omitempty"`
}

func (s *Service) renderProduct(ctx context.Context, id string) ProductPage {
    // Critical path — must succeed
    prod, _  := s.products.Get(ctx, id)
    price, _ := s.pricing.Get(ctx, id)
    page := ProductPage{Product: prod, Price: price}

    // Optional — short timeout, swallow errors, mark as degraded.
    if s.flags.RecommendationsEnabled.Load() {
        cctx, cancel := context.WithTimeout(ctx, 100*time.Millisecond)
        defer cancel()
        if recs, err := s.recs.For(cctx, id); err == nil {
            page.Recommendations = recs
        } else {
            page.DegradedFeatures = append(page.DegradedFeatures, "recommendations")
        }
    }

    // Reviews: try fresh, fall back to cached, then hide entirely.
    if s.flags.ReviewsEnabled.Load() {
        page.Reviews = s.reviewsOrCached(ctx, id)
    }
    return page
}

Load shedding & backpressure

Core Defense
Difficulty

The story

Demand exceeds capacity in two situations: a sudden spike (Black Friday, viral tweet) or a slow downstream that backs up your queue. Both have the same failure mode if unhandled: requests pile up, latency tanks, healthchecks fail, instances get killed, traffic shifts to fewer instances, and the cascade goes brrr. Load shedding handles the spike: when the queue is full, return 503 for low-priority traffic immediately. Don't pretend you can serve them in 30 seconds — fail fast.

Backpressure handles the slow downstream: when the consumer is saturated, it tells the producer "slow down" via blocking, semaphores, or HTTP/2 flow control. Reactive frameworks (Reactor, RxJava, asyncio with bounded queues) bake this in. The general rule: shed at the edge, push back inside. The gateway sheds noisy clients with 503s; internal services use bounded concurrency to never overwhelm each other.

Use when
  • Bounded queues + bounded concurrency on every service
  • Priority lanes — health probes never sit behind analytics
  • Adaptive concurrency (e.g., Netflix concurrency-limits)
Avoid
  • Unbounded queues — they hide the problem until OOM
  • Identical timeouts everywhere — head-of-line blocking
  • Shedding without metrics on what got dropped
Connects to Circuit breaker, Rate limit, Degradation
// Bounded concurrency + load shedding via semaphore.
type SheddingHandler struct {
    sem      chan struct{}                    // concurrency cap
    priority func(*http.Request) int          // 0 = high, 9 = low
    next     http.Handler
}

func NewShedder(max int, next http.Handler) *SheddingHandler {
    return &SheddingHandler{
        sem:      make(chan struct{}, max),
        next:     next,
        priority: defaultPriority,
    }
}

func (h *SheddingHandler) ServeHTTP(w http.ResponseWriter, r *http.Request) {
    // Try to acquire a slot — if the queue would block, shed low-pri.
    select {
    case h.sem <- struct{}{}:
        defer func() { <-h.sem }()
        h.next.ServeHTTP(w, r)
    default:
        // At capacity. High-priority callers wait briefly, low-pri 503.
        if h.priority(r) < 3 {
            select {
            case h.sem <- struct{}{}:
                defer func() { <-h.sem }()
                h.next.ServeHTTP(w, r)
            case <-time.After(50 * time.Millisecond):
                w.Header().Set("Retry-After", "1")
                http.Error(w, "overloaded", 503)
            }
        } else {
            w.Header().Set("Retry-After", "5")
            http.Error(w, "overloaded", 503)
        }
    }
}

import asyncio
from fastapi import FastAPI, Request, HTTPException

app = FastAPI()

# Cap concurrent in-flight work in this service
SLOTS           = asyncio.Semaphore(100)
SHED_THRESHOLD  = 10                                # queue depth to shed at

@app.middleware("http")
async def shed_or_run(req: Request, call_next):
    # Health probes always pass — they're how we get fixed!
    if req.url.path in ("/health", "/ready"):
        return await call_next(req)

    # Heuristic: queue depth ≈ tasks waiting on semaphore
    if SLOTS._value == 0 and priority(req) > 3:
        raise HTTPException(503, headers={"Retry-After": "5"})

    try:
        async with asyncio.timeout(0.05):                # brief wait
            await SLOTS.acquire()
    except TimeoutError:
        raise HTTPException(503, headers={"Retry-After": "1"})

    try:
        return await call_next(req)
    finally:
        SLOTS.release()

def priority(req: Request) -> int:
    # 0 = critical (auth, checkout); 9 = nice-to-have (analytics)
    if req.url.path.startswith("/v1/checkout"): return 0
    if req.url.path.startswith("/v1/analytics"): return 9
    return 5

        // Health probes bypass the bulkhead

            hres.sendError(503, "overloaded");

        } finally {

        }
    }

Deployment strategies

Core Practical
Difficulty

The story

The riskiest moment in any service's life is deploy time. Rolling updates restart pods one batch at a time — simplest, but a bad version reaches some users immediately. Blue/green spins up the new version on the side and atomically swaps traffic at the load balancer — instant rollback, but you pay for double capacity for the duration. Canary sends a small fraction (1–5%) to the new version, watches the golden signals, and either advances the percentage or rolls back automatically.

Modern platforms (Argo Rollouts, Flagger, Spinnaker) automate the canary with metric analysis: at each step, compare canary's error rate and latency to the stable fleet. If they diverge, abort and roll back. The core insight: let metrics, not humans, decide promotion. Humans miss subtle regressions; a 5% increase in p99 latency on 5% of traffic is statistically obvious to a tool, easy to miss on a dashboard.

Use when
  • Canary with metric-based promotion (Flagger / Argo Rollouts)
  • Blue/green for stateful tier-zero services
  • Feature flags for risky business logic, decoupled from deploy
Avoid
  • "Deploy + watch dashboards" — manual gates miss regressions
  • Schema migrations during canary (use expand/contract)
  • Canary with too little traffic — no statistical signal
Connects to SLO budgets, Migrations, Golden signals

@app.get("/health/ready")                    # readiness — take traffic?
async def ready(resp: Response):

    if not _warmed:
        resp.status_code = 503
        return {"status": "warming"}
    # Slow ramp prevents the canary from drowning on connection burst
    age = time.monotonic() - _started_at
    if age < 15:
        resp.status_code = 503
        return {"status": "stabilising"}
    return {"status": "ready"}

    global _warmed

Zero-downtime migrations

Core Discipline
Difficulty

The story

The fastest way to take down production is a "simple" rename. The deploy goes out, the app expects email_v2, but the old version still running on half the pods writes email, and now half your users have data in the wrong column. Zero-downtime migrations require that any running version of the app — old or new — keeps working at every intermediate step.

The pattern is expand → dual-write → switch reads → contract, with each phase a separate deploy days or weeks apart. Expand: add the new column nullable, no FK, no constraint. Dual-write: app writes both old and new; backfill historical rows in batches. Switch reads: behind a feature flag, point reads at the new column; verify parity, then make it permanent. Contract: only when no code references the old name does the column get dropped. The same shape works for renames, type changes, and splitting/merging tables.

Use when
  • Any column rename, retype, or split — never atomic
  • Add column nullable; tighten constraint in a later deploy
  • Online migration tools (gh-ost, pt-online-schema-change)
Avoid
  • Rename + deploy + drop in one PR — old pods break
  • Adding NOT NULL without a default on huge tables
  • Long-running ALTERs without lock_timeout / statement_timeout
Connects to Deployments, Data storage, Schema evolution
// Phase 2: dual-write while a backfill job runs in the background.

type UserRepo struct { db *sql.DB }

// During dual-write, every UPDATE/INSERT touches both columns.
func (r *UserRepo) UpdateEmail(ctx context.Context,
    id int64, email string) error {
    _, err := r.db.ExecContext(ctx, `
        UPDATE users SET email_old = $1, email_new = $1 WHERE id = $2
    `, email, id)
    return err
}

// Backfill — small batches, bounded blast radius.
func Backfill(ctx context.Context, db *sql.DB) error {
    for {
        res, err := db.ExecContext(ctx, `
            UPDATE users
               SET email_new = email_old
             WHERE id IN (
                 SELECT id FROM users
                  WHERE email_new IS NULL
                  ORDER BY id LIMIT 1000        -- small batch!
             )
        `)
        if err != nil { return err }
        n, _ := res.RowsAffected()
        if n == 0 { return nil }      // done
        time.Sleep(100 * time.Millisecond)    // don't saturate I/O
    }
}

// Phase 3: read switch behind a flag (PR per phase, deploy in between).
func (r *UserRepo) GetEmail(ctx context.Context, id int64) (string, error) {
    col := "email_old"
    if flags.Enabled("users.read_email_new") {
        col = "email_new"
    }
    var e string
    return e, r.db.QueryRowContext(ctx,
        fmt.Sprintf("SELECT %s FROM users WHERE id = $1", col),
        id).Scan(&e)
}

Incident response & postmortems

Bonus Discipline
Difficulty

The story

Incidents are inevitable. The question is whether each one teaches you something. MTTD (mean time to detect) measures your monitoring; MTTR (mean time to recover) measures your runbooks; MTTL (mean time to learn) measures whether you actually changed anything afterwards. The first two are technical; the third is cultural.

During the incident: appoint an incident commander who doesn't fix anything — they coordinate, communicate, and decide. Mitigate first (roll back, fail open, shed load), debug second. Time-box hero efforts: 15 minutes of trying clever fixes, then revert. After the dust settles, write a blameless postmortem within a week — not "Alice deployed bad code" but "the deploy pipeline allowed an untested config change to reach production". Action items get owners and due dates, or they don't exist. Track the percentage of postmortem actions you actually ship — anything under 80% is a culture problem.

Use when
  • Incident commander role separated from fixers
  • Status page / customer comms within 15 minutes
  • Blameless postmortems with tracked action items
Avoid
  • Naming individuals as the "cause" — fix the system
  • Postmortem actions that are just "be more careful"
  • Calling it minor and skipping the writeup
Connects to SLOs, Deployments, Circuit breaker
// Mitigation toggle: a single env-var flip can disable an offending feature
// or whole tenant during an incident. The on-call doesn't deploy code at 3am.

type KillSwitch struct {
    Disabled       atomic.Bool
    DisabledTenants sync.Map           // tenant -> bool
}

func (k *KillSwitch) Allow(tenant string) bool {
    if k.Disabled.Load() { return false }
    _, isolated := k.DisabledTenants.Load(tenant)
    return !isolated
}

// Watch a config map / consul key — flip without redeploy.
func (k *KillSwitch) Watch(ctx context.Context, cfg *consul.Client) {
    cfg.Watch("kill/global", func(v string) {
        k.Disabled.Store(v == "true")
    })
    cfg.Watch("kill/tenants", func(v string) {
        k.DisabledTenants.Range(func(k, _ interface{}) bool {
            k.DisabledTenants.Delete(k); return true
        })
        for _, t := range strings.Split(v, ",") {
            k.DisabledTenants.Store(t, true)
        }
    })
}
