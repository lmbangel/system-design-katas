Fast is a feature.

Performance isn't an afterthought you bolt on at launch. It's latency numbers memorised, profiles read, caches designed, queries planned, and load tested — before the pager goes off at 3am because page 50 of your API does a sequential scan.

PRINCIPLE 01

Measure before you optimise.

Intuition lies. Profile the hot path, benchmark the change, ship the proof. "It feels faster" is not a metric.

PRINCIPLE 02

The fastest call is the one you don't make.

Cache hits, batched queries, precomputed views — every eliminated round-trip is latency you'll never have to debug.

PRINCIPLE 03

Scale sideways first.

Vertical scaling buys you one bigger machine. Horizontal scaling buys you infinity — if your data model allows it. Design for statelessness early.

PRINCIPLE 04

Tail latency is the real latency.

p50 is marketing. p99 is what your slowest 1% of users actually experience — and at scale, that's millions of people.

01

Latency numbers every engineer should know

Core Mental model
Difficulty

The story

These numbers aren't trivia — they're the physics of your architecture. An L1 cache reference takes ~1ns. A Redis GET takes ~500µs. That's a 500,000× gap. A cross-region call is 100ms — enough for a user to notice. Every architectural decision (cache locally vs cache in Redis vs fetch from DB vs call another service) is a trade-off along this spectrum.

The practical implications: avoid network hops in hot paths — batch, coalesce, cache locally when you can. SSD is 100× faster than HDD for random reads — know your storage tier. Same-DC is 300× faster than cross-region — design multi-region carefully. And external APIs are the slowest thing you control — always wrap them in a timeout + circuit breaker + cache.

▲ Keep in mind
  • 1 DB query = ~1,000 Redis GETs = ~1,000,000 L1 refs
  • Same-DC network: ~0.5ms. Cross-region: ~100ms. 200×.
  • External APIs: budget 200ms+, always with timeout + fallback
▼ Avoid
  • Assuming "the network is fast" — it's the slowest thing
  • Multiple sequential external API calls in one request
  • Skipping local caches because Redis is "fast enough"
Connects to Caching, Pooling, CDN
// Two-tier cache: local → Redis → DB. Each tier is 100–1000× slower.
type ProductCache struct {
    local  *ristretto.Cache     // in-process, ~100ns
    redis  *redis.Client        // same-DC, ~0.5ms
    db     *sql.DB              // same-DC, ~2ms
}

func (c *ProductCache) Get(ctx context.Context, id string) (*Product, error) {
    // Tier 1: local — sub-microsecond
    if v, ok := c.local.Get(id); ok {
        return v.(*Product), nil
    }
    // Tier 2: Redis — ~0.5ms
    data, err := c.redis.Get(ctx, "product:"+id).Bytes()
    if err == nil {
        var p Product
        json.Unmarshal(data, &p)
        c.local.SetWithTTL(id, &p, 1, 10*time.Second)   // short local TTL
        return &p, nil
    }
    // Tier 3: DB — ~2ms+
    p, err := loadProductFromDB(ctx, c.db, id)
    if err != nil { return nil, err }
    // Backfill both tiers
    data, _ = json.Marshal(p)
    c.redis.Set(ctx, "product:"+id, data, 5*time.Minute)
    c.local.SetWithTTL(id, p, 1, 10*time.Second)
    return p, nil
}

from cachetools import TTLCache
import redis.asyncio as aioredis, json

_local = TTLCache(maxsize=2048, ttl=10)           # in-process, ~100ns
_redis = aioredis.from_url("redis://localhost")   # same-DC, ~0.5ms

async def get_product(pid: str) -> dict:
    # Tier 1 — local process memory
    if pid in _local:
        return _local[pid]

    # Tier 2 — Redis
    raw = await _redis.get(f"product:{pid}")
    if raw:
        p = json.loads(raw)
        _local[pid] = p
        return p

    # Tier 3 — database
    p = await db.fetchrow("SELECT * FROM products WHERE id = $1", pid)
    p = dict(p)
    await _redis.set(f"product:{pid}", json.dumps(p), ex=300)
    _local[pid] = p
    return p
// Caffeine (local) + Redis (shared) + JPA (DB).

@Service
public class ProductCache {
    private final Cache<String, Product> local = Caffeine.newBuilder()
        .maximumSize(2048)
        .expireAfterWrite(Duration.ofSeconds(10))
        .build();

    private final RedisTemplate<String, Product> redis;
    private final ProductRepo repo;

    public Product get(String id) {
        // Tier 1: Caffeine — sub-µs
        Product p = local.getIfPresent(id);
        if (p != null) return p;

        // Tier 2: Redis — ~0.5ms
        p = redis.opsForValue().get("product:" + id);
        if (p != null) { local.put(id, p); return p; }

        // Tier 3: DB — ~2ms+
        p = repo.findById(id).orElseThrow();
        redis.opsForValue().set("product:" + id, p,
            Duration.ofMinutes(5));
        local.put(id, p);
        return p;
    }
}
02

Profiling & flame graphs

CoreTool
Difficulty

The story

A flame graph is a visualisation of stack-trace samples. Width is proportional to time spent — the widest bars are the hot path. Reading one: the x-axis isn't time, it's alphabetical. Height is stack depth. A "plateau" (wide bar at the top) means a function consuming CPU/wall-time. A tall skinny tower means deep recursion that's actually fast.

CPU profiles show compute-bound bottlenecks. Wall-clock profiles (or "off-CPU" profiles) show time spent waiting for I/O, locks, or network. In Go, pprof gives you both. In Java, async-profiler is the gold standard. In Python, py-spy attaches to a running process without restart. The senior move: run continuous profiling in production (Pyroscope, Datadog Continuous Profiler) and compare flame graphs before/after a release.

▲ Use when
  • Go: pprof → CPU + alloc + goroutine profiles
  • Java: async-profiler → flame graph + allocation
  • Python: py-spy → attach to running PID
▼ Avoid
  • Optimising code you haven't profiled — you'll optimise the wrong thing
  • Profiling only in dev — prod traffic patterns are different
  • Micro-benchmarks without realistic data sizes
Connects to Latency numbers, N+1, Tracing

The N+1 query problem

CoreTrap
Difficulty

The story

You load 100 orders. For each order, you load the user. That's 1 + 100 = 101 database round-trips. At 2ms per query, that's 200ms. A JOIN does it in one round-trip (~3ms). ORMs hide this trap behind innocent-looking lazy-loaded relationships: order.user.name triggers a query per loop iteration.

Three fixes: JOIN when the relationship is always needed. Batch (WHERE id IN (...)) when you need them separately. DataLoader (GraphQL pattern) coalesces individual lookups within a single tick into one batch query. The senior move: log slow queries in dev and alert on query counts per request — if one endpoint issues 50+ queries, it's almost certainly N+1.

▲ Use when
  • JOIN for always-needed relations
  • Batch IN() for optional related entities
  • DataLoader for GraphQL resolver fan-out
▼ Avoid
  • Lazy loading in loops — the classic ORM trap
  • Assuming the ORM "knows" to batch — it usually doesn't
  • Ignoring query counts in dev — add a query counter middleware
Connects to Indexes, Pagination

Cache strategies

CoreArchitecture
Difficulty

The story

Cache-aside (lazy loading): the app checks the cache first; on miss, fetches from DB and backfills the cache. The app owns all logic. This is the default pattern — use it unless you have a reason not to. Write-through: on write, the app updates cache and DB synchronously. The cache is always warm, but writes are slower. Write-behind: writes go to cache only; a background process drains to DB. Maximum write throughput, but cache crash = lost writes.

Invalidation is the hard part. TTL is the simplest — accept stale data for N seconds. Event-driven invalidation (CDC from DB → cache delete) gives near-real-time freshness but adds complexity. Cache stampede: when a popular key expires, 1,000 requests all miss simultaneously and hammer the DB. Mitigate with lock-based cache fill (only one request recomputes, others wait) or probabilistic early refresh.

▲ Use when
  • Cache-aside: default for most read-heavy workloads
  • TTL + event-based invalidation for freshness
  • Lock-based fill to prevent cache stampede
▼ Avoid
  • Write-behind without durable queues (data loss risk)
  • Caching without a TTL — stale data forever
  • "Cache everything" — cache the hot path, benchmark the rest
Connects to Latency, HTTP caching, CDN
// Cache-aside with stampede protection via singleflight.
import "golang.org/x/sync/singleflight"

type CachedProducts struct {
    cache  *redis.Client
    db     *sql.DB
    flight singleflight.Group   // prevents stampede
}

func (c *CachedProducts) Get(ctx context.Context, id string) (*Product, error) {
    // 1. Check cache
    data, err := c.cache.Get(ctx, "product:"+id).Bytes()
    if err == nil { return decode(data) }

    // 2. Cache miss → one-at-a-time DB fetch (no stampede)
    v, err, _ := c.flight.Do(id, func() (interface{}, error) {
        p, err := loadFromDB(ctx, c.db, id)
        if err != nil { return nil, err }
        // 3. Backfill cache
        b, _ := json.Marshal(p)
        c.cache.Set(ctx, "product:"+id, b, 5*time.Minute)
        return p, nil
    })
    if err != nil { return nil, err }
    return v.(*Product), nil
}

// On write: invalidate cache (don't try to update it)
func (c *CachedProducts) Invalidate(ctx context.Context, id string) {
    c.cache.Del(ctx, "product:"+id)
}
# Cache-aside + asyncio.Lock for stampede protection.
import asyncio, json
import redis.asyncio as aioredis
from collections import defaultdict

_redis = aioredis.from_url("redis://localhost")
_locks: dict[str, asyncio.Lock] = defaultdict(asyncio.Lock)

async def get_product(pid: str) -> dict:
    # 1. Check cache
    raw = await _redis.get(f"product:{pid}")
    if raw:
        return json.loads(raw)

    # 2. Stampede guard — only one fills the cache
    async with _locks[pid]:
        # Double-check after acquiring lock
        raw = await _redis.get(f"product:{pid}")
        if raw:
            return json.loads(raw)

        # 3. Load from DB + backfill
        p = await db.fetchrow("SELECT * FROM products WHERE id=$1", pid)
        p = dict(p)
        await _redis.set(f"product:{pid}", json.dumps(p), ex=300)
        return p

@Service
public class ProductService {

        return repo.save(product);
    }
}

05

Connection pooling

CorePractical
Difficulty

The story

Opening a database connection costs ~8ms (TCP + TLS + auth). At 1,000 requests/second, that's 8 seconds of pure overhead. A connection pool opens N connections at startup and lends them to workers. When the worker is done, the connection goes back to the pool — the next worker skips the handshake entirely.

The hard question is how big. Too small: workers queue up waiting for a connection, adding latency. Too big: you overwhelm the database with concurrent connections and everything slows down. The HikariCP formula — pool = CPU cores × 2 + disk_spindles — is a good start. For Postgres, max_connections is global across all clients; use PgBouncer as a proxy pooler if you have many app instances. Always set a connection_timeout so workers get a fast 503 instead of hanging.

▲ Use when
  • HikariCP (Java), pgxpool (Go), asyncpg (Python)
  • PgBouncer between app and Postgres in multi-pod setups
  • Monitor pool saturation as a golden signal
▼ Avoid
  • Opening a new connection per request
  • Pool size = max_connections — leave room for admin/migrations
  • No connection_timeout — threads hang forever
Connects to Latency, Golden signals

Async vs sync I/O

CoreModel
Difficulty

The story

Synchronous I/O blocks the thread while waiting for a response. One thread per request, each thread owns ~1MB of stack. At 10,000 concurrent connections, that's 10GB just for stacks. Asynchronous I/O (event loop) registers a callback or future and yields the thread to handle other work. One thread can manage thousands of connections because it's never idle — it just switches between ready I/O.

The choice depends on your language: Go gives you goroutines — lightweight green threads multiplexed onto OS threads. You write blocking-looking code but the runtime makes it non-blocking. Java 21 virtual threads (Loom) do the same. Python asyncio is a true event loop — you must use async/await throughout and avoid blocking calls. Thread-per-request is fine below ~1,000 concurrent connections — don't over-engineer if you're not at scale.

▲ Use when
  • Go: goroutines by default — no choice needed
  • Java 21+: virtual threads for I/O-bound services
  • Python: asyncio + uvicorn for I/O-heavy APIs
▼ Avoid
  • Async for CPU-bound work — use a thread/process pool
  • Mixing blocking calls inside async code (kills the loop)
  • Async for a 100-user internal tool — overkill
Connects to Pooling, Batching, Load shedding

07

Batching & streaming

CorePattern
Difficulty

The story

Every round-trip has fixed overhead: TCP, serialisation, context switch. Batching amortises that cost by collecting N items and sending them in one call. Trade-off: you add latency (waiting to fill the batch) to gain throughput. The two knobs: batch_size (flush when N items) and flush_interval (flush every T ms, whichever comes first). Too large: memory pressure. Too small: you're back to one-by-one.

Streaming removes the flush entirely — items flow continuously through a pipe (Kafka, gRPC server-streaming, WebSocket). It's ideal when data is unbounded and latency matters more than throughput. The catch: you need backpressure (see page 05) to prevent the producer from overwhelming the consumer. Every streaming system is either a batch under the hood (Kafka fetches in batches) or requires flow-control (gRPC, Reactive Streams).

▲ Use when
  • Batch: DB inserts (COPY), SQS (up to 10 msgs), bulk API calls
  • Stream: real-time logs, CDC, price feeds, chat
  • Tune batch_size + flush_interval together
▼ Avoid
  • Unbounded batches — cap size and flush on timer
  • Streaming without backpressure — the consumer will OOM
  • Batch size = 1 — that's just one-by-one with extra overhead
Connects to Event sourcing, Backpressure
// Batch inserter: flush on size or interval.
type BatchInserter struct {
    mu    sync.Mutex
    buf   []Event
    db    *pgxpool.Pool
    size  int
    flush time.Duration
}

func (b *BatchInserter) Add(e Event) {
    b.mu.Lock()
    b.buf = append(b.buf, e)
    if len(b.buf) >= b.size {
        b.flushLocked()
    }
    b.mu.Unlock()
}

func (b *BatchInserter) Start(ctx context.Context) {
    t := time.NewTicker(b.flush)
    for {
        select {
        case <-t.C:
            b.mu.Lock(); b.flushLocked(); b.mu.Unlock()
        case <-ctx.Done():
            b.mu.Lock(); b.flushLocked(); b.mu.Unlock(); return
        }
    }
}

func (b *BatchInserter) flushLocked() {
    if len(b.buf) == 0 { return }
    // pgx COPY for max throughput
    _, _ = b.db.CopyFrom(context.Background(),
        pgx.Identifier{"events"}, []string{"id", "type", "data"},
        pgx.CopyFromSlice(len(b.buf), func(i int) ([]interface{}, error) {
            e := b.buf[i]
            return []interface{}{e.ID, e.Type, e.Data}, nil
        }))
    b.buf = b.buf[:0]
}
# asyncio batch: collect events, flush on size or timer.
import asyncio

class BatchWriter:
    def __init__(self, db, size=500, interval=0.1):
        self.db, self.size, self.interval = db, size, interval
        self.buf: list = []
        self._task = asyncio.create_task(self._ticker())

    async def add(self, event):
        self.buf.append(event)
        if len(self.buf) >= self.size:
            await self._flush()

    async def _ticker(self):
        while True:
            await asyncio.sleep(self.interval)
            await self._flush()

    async def _flush(self):
        if not self.buf: return
        batch, self.buf = self.buf, []
        # asyncpg COPY is the fastest bulk insert
        await self.db.copy_records_to_table(
            "events", records=[(e.id, e.type, e.data) for e in batch],
            columns=["id", "type", "data"])
// Spring Batch or manual buffer + scheduled flush.

@Component
public class EventBatcher {
    private final JdbcTemplate jdbc;
    private final List<Event> buf = new CopyOnWriteArrayList<>();

    public void add(Event e) {
        buf.add(e);
        if (buf.size() >= 500) flush();
    }

    @Scheduled(fixedRate = 100)     // every 100ms
    public synchronized void flush() {
        if (buf.isEmpty()) return;
        List<Event> batch = new ArrayList<>(buf);
        buf.clear();
        jdbc.batchUpdate(
            "INSERT INTO events (id, type, data) VALUES (?, ?, ?)",
            new BatchPreparedStatementSetter() {
                public void setValues(PreparedStatement ps, int i) throws SQLException {
                    ps.setString(1, batch.get(i).id());
                    ps.setString(2, batch.get(i).type());
                    ps.setString(3, batch.get(i).data());
                }
                public int getBatchSize() { return batch.size(); }
            });
    }
}
08

CDN & edge caching

CoreInfra
Difficulty

The story

A CDN is a global network of caching proxies. The user's request hits the nearest edge node. If the content is cached: served in ~10ms, origin never touched. If not: the edge fetches from origin, caches the response, and serves it — plus every subsequent user in that region gets the cached version. For static assets (JS, CSS, images), this is a 100× latency reduction and near-zero origin load.

For APIs: Cache-Control: public, s-maxage=300 lets the CDN cache a response for 5 minutes while browsers use max-age for shorter freshness. stale-while-revalidate serves the old copy while fetching a new one in the background — users never see a cache miss. The pitfall: caching user-specific responses as public leaks data between users. Always set Vary: Authorization or private on authenticated responses. For purging: use surrogate keys (Fastly, Cloudflare) to invalidate groups of URLs in one call.

▲ Use when
  • Static assets: content-hashed filenames + immutable
  • API lists: s-maxage + stale-while-revalidate
  • Surrogate keys for targeted cache purging
▼ Avoid
  • public on authenticated/user-specific responses
  • Purging by URL pattern — use surrogate keys
  • No Cache-Control header — default behaviour is undefined
Connects to HTTP caching, Cache strategies

09

Hot keys & shard skew

CoreTrap
Difficulty

The story

You shard your database or cache to spread load across nodes. But sharding only works if the keys are uniformly distributed. A hot key — a celebrity's profile, a viral product, a timestamp-based partition — lands all traffic on one shard while the others idle. That shard saturates and becomes the bottleneck for the whole system.

The fix depends on the cause. Random suffix: split product:42 into product:42:0 through product:42:7, read from a random replica. Local cache: for read-hot keys, cache in-process so the shard only sees one request per TTL. Better shard key: never shard on timestamp or sequential ID — use a high-entropy key (UUID, hash of entity ID). Monitor shard load distribution as a first-class metric.

▲ Use when
  • Shard key = hash(entity_id) for uniform distribution
  • Local cache for read-hot keys (celebrity profiles, config)
  • Monitor per-shard CPU/QPS — alert on skew > 2×
▼ Avoid
  • Timestamp or sequential ID as shard key
  • Ignoring hot-key metrics until production melts
  • Single Redis key for global counters (use INCR with suffixes)
Connects to Sharding, Caching
// Hot-key mitigation: split a hot key into N replicas.
const hotKeyReplicas = 8

func hotKeyGet(ctx context.Context, rdb *redis.Client, key string) (string, error) {
    // Read from a random replica to spread load
    shard := rand.Intn(hotKeyReplicas)
    return rdb.Get(ctx, fmt.Sprintf("%s:%d", key, shard)).Result()
}

func hotKeySet(ctx context.Context, rdb *redis.Client,
    key, val string, ttl time.Duration) {
    // Write to ALL replicas
    pipe := rdb.Pipeline()
    for i := 0; i < hotKeyReplicas; i++ {
        pipe.Set(ctx, fmt.Sprintf("%s:%d", key, i), val, ttl)
    }
    pipe.Exec(ctx)
}

import random

HOT_KEY_REPLICAS = 8

async def hot_get(redis, key: str) -> str | None:
    shard = random.randint(0, HOT_KEY_REPLICAS - 1)
    return await redis.get(f"{key}:{shard}")

async def hot_set(redis, key: str, val: str, ttl: int = 60):
    async with redis.pipeline() as p:
        for i in range(HOT_KEY_REPLICAS):
            p.set(f"{key}:{i}", val, ex=ttl)
        await p.execute()

@Service
public class HotKeyCache {
    private static final int REPLICAS = 8;
    private final StringRedisTemplate redis;
    private final ThreadLocalRandom rng = ThreadLocalRandom.current();

    public String get(String key) {
        int shard = rng.nextInt(REPLICAS);
        return redis.opsForValue().get(key + ":" + shard);
    }

    public void set(String key, String val, Duration ttl) {
        redis.executePipelined((RedisCallback<Void>) conn -> {
            for (int i = 0; i < REPLICAS; i++)
                conn.stringCommands().set(
                    (key + ":" + i).getBytes(),
                    val.getBytes());
            return null;
        });
    }
}

10

Load testing

BonusDiscipline
Difficulty

The story

Every system has a knee (the RPS where latency starts climbing non-linearly) and a cliff (the RPS where errors spike and the system falls over). If you don't know where yours are, your first real traffic spike will find them for you — in production. Load testing finds both in a controlled environment.

The discipline: ramp RPS linearly while measuring p50/p95/p99 latency and error rate. The knee is where p99 diverges from p50. The cliff is where errors jump. Your capacity is some safety margin below the knee (typically 70%). Run this on every release — performance regressions are invisible without a baseline. Use k6 (code-first, developer-friendly), Locust (Python), or Gatling (JVM). Test with realistic data, realistic think-times, and warm caches — a load test against an empty cache tells you nothing useful.

▲ Use when
  • k6 / Locust / Gatling — pick one, run it in CI
  • Ramp RPS until you find the knee + cliff
  • Compare baseline vs release — catch regressions
▼ Avoid
  • Testing with empty caches / empty databases
  • Fixed concurrency instead of ramping RPS
  • Only testing happy paths — test error paths under load too
Connects to SLOs, Load shedding

class ProductSimulation extends Simulation {

  val httpConf = http.baseUrl("https://api.example.com")

  val browse = scenario("Browse")
    .exec(http("list products").get("/v1/products")
      .check(status.is(200)))
    .pause(1, 3)     // 1-3 second think time

  setUp(
    browse.inject(
      rampUsersPerSec(10).to(500).during(300),  // 5min ramp
      constantUsersPerSec(500).during(300),    // 5min steady
      rampUsersPerSec(500).to(2000).during(300), // push to cliff
    )

   .assertions(

   )
