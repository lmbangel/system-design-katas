Applied system design · Architecture

One problem, three right answers.

Northwind Cold Chain has three entities, six source databases, one network that lets nothing in, and a finance team that will reject any number that does not match the ERP. This page designs its data platform three times: lean on a single node, built for scale and minutes-fresh data, and bought as a managed Microsoft service. The interview point is not which one wins. It is showing which constraint picks which design, what each one costs to run, and how to move between them without a rewrite.

PRINCIPLE 01

Constraints pick the architecture.

The same requirements have several right answers. Name the data size, the freshness someone will pay for, the team and the estate first; the boxes follow.

PRINCIPLE 02

The ERP is the truth; prove you agree.

A dashboard that disagrees with the trial balance by one rand is wrong, and finance will stop trusting all of it. Reconcile automatically, on every load.

PRINCIPLE 03

Push across trust boundaries.

Pulling needs an inbound path; pushing needs one outbound HTTPS rule. Make every landing idempotent so a retry is always free.

PRINCIPLE 04

One set of permissions, every door.

Power BI, analysts and the AI assistant read through the same entitlement table, as the user. An assistant on a service account is a data leak with a chat window.

01

Requirements, constraints and the shape of the answer

Start hereRequirements
Difficulty

The story

Start where an interviewer wants you to start: with questions, not boxes. Northwind Cold Chain runs three entities, South Africa (ZAR), Namibia (NAD) and Botswana (BWP), each with its own ERP on SQL Server and its own warehouse management system. The functional asks are three: one set of Power BI dashboards across entities, a month-end pack that reconciles to each ERP to the cent, and an AI assistant that answers questions over the same data with the asking user's own permissions. Then the awkward one: the Botswana ERP sits in a hosted network that allows no inbound connections at all.

The non-functional numbers decide the architecture, so write them down. About 185 000 changed ERP rows and 1.35 million WMS movements a day: roughly 36 GB a year as compressed Parquet, 250 GB across seven years of retention. Daily freshness for finance, hourly for operations. About 60 dashboard users, 40 assistant users, two data engineers. Multi-currency means storing three amounts per line: the transaction currency, the entity's functional currency (what the ERP books, and the only thing you reconcile), and group ZAR (converted at a recorded rate, and never reconciled against).

The same requirements, three constraint sets. A, lean: today's numbers, two engineers, a small budget. B, scale and freshness: ten times the data after an acquisition and cold-room telemetry, operations dashboards fresh within minutes, several teams building models. C, managed: a small team inside a Microsoft estate whose leadership would rather buy than build. The next three deep-dives design each one; the four after that solve what all three share: the closed network, proving the numbers, security, and choosing.

Ask first
  • Which number must match what, and to what tolerance?
  • How fresh, and for whom? Finance and operations rarely want the same answer
  • Who may see which entity, and does the assistant inherit that?
  • What can each network reach, and in which direction?
Interview red flags
  • Drawing Kafka before asking about data volume
  • Reconciling converted ZAR instead of functional currency
  • Treating the AI assistant as a separate system with its own access

# Back-of-envelope sizing: the numbers that decide between A, B and C.
# Plain Python on purpose: a calculation you rerun whenever the inputs move.
from dataclasses import dataclass


@dataclass(frozen=True)
class Source:
    name: str
    rows_per_day: int       # changed rows per day, not table size
    bytes_per_row: int      # compressed Parquet, measured on a sample batch


SOURCES = [
    Source("erp-za", 120_000, 90),
    Source("erp-na", 40_000, 90),
    Source("erp-bw", 25_000, 90),
    Source("wms-za", 900_000, 60),
    Source("wms-na", 300_000, 60),
    Source("wms-bw", 150_000, 60),
]

RETENTION_YEARS = 7             # finance keeps seven years
ONE_NODE_COMFORT_GB = 500       # what one large VM running DuckDB scans comfortably


def gb_per_year(sources: list[Source]) -> float:
    return sum(s.rows_per_day * s.bytes_per_row * 365 for s in sources) / 1e9


def summary(growth: float = 1.0) -> dict[str, float | str]:
    per_year = gb_per_year(SOURCES) * growth
    retained = per_year * RETENTION_YEARS
    return {
        "gb_per_year": round(per_year, 1),
        "gb_retained": round(retained, 1),
        "fits_one_node": "yes" if retained < ONE_NODE_COMFORT_GB else "no",
    }


if __name__ == "__main__":
    print("today:", summary())        # ~36 GB/yr, ~250 GB retained  -> A fits
    print("10x:  ", summary(10.0))    # ~356 GB/yr, ~2.5 TB retained -> B or C territory

02

Version A, lean: push agents, Parquet, DuckDB and dbt

CoreVersion A
Difficulty

The story

When the data fits on one machine, use one machine. Each entity runs a small push agent beside its SQL Servers that reads changes with change tracking and uploads Parquet batches over HTTPS (deep-dive 05). Object storage holds the landed files, partitioned by source, table and entity. A single VM runs DuckDB and dbt: staging views read the Parquet directly, intermediate models convert currencies and conform dimensions, and marts are built as tables. The finished gold tables are copied into a small Postgres database, which is what Power BI and the assistant's tools connect to.

Why DuckDB: it is columnar and vectorised, reads Parquet straight from object storage, and at 250 GB a full rebuild of the finance marts takes minutes on a 32 GB VM. dbt adds SQL models in Git, tests, documentation and lineage. Why the separate marts database: DuckDB is an in-process engine with a single writer, so it makes a poor concurrent server for 60 dashboard users, and Postgres is a very good one. Rebuild the marts in full every night rather than incrementally. At this size it is cheap, and a full rebuild cannot slowly accumulate incremental-logic bugs.

Trade-off: one node is a single point of failure and a hard ceiling. That is acceptable while the rebuild window is measured in hours and recovery is "start a new VM and rerun": the landed Parquet is the durable copy and the DuckDB file is disposable. It stops being acceptable when the nightly run creeps towards its window, when operations want data within minutes, or when a third team starts committing models into the same project.

Use when
  • Under about a terabyte scanned, one or two engineers
  • Daily or hourly freshness is genuinely enough
  • Cost and simplicity matter more than elasticity
Avoid
  • Serving dashboards straight from the DuckDB file
  • Several teams writing into one project with no isolation
  • A minutes-fresh requirement someone has actually funded

# orchestration.py: one process, one schedule, one VM.
# Plain Python (Dagster), not a web service: nothing calls it, it runs on a clock.
from pathlib import Path

import duckdb
from dagster import AssetExecutionContext, Definitions, ScheduleDefinition, asset, define_asset_job
from dagster_dbt import DbtCliResource, DbtProject, dbt_assets

PROJECT = DbtProject(project_dir=Path(__file__).parent / "northwind_dbt")
GOLD_TABLES = ("fct_gl_monthly", "fct_stock_daily", "dim_entity", "dim_account")


@dbt_assets(manifest=PROJECT.manifest_path)
def northwind_models(context: AssetExecutionContext, dbt: DbtCliResource):
    # build = run + test in DAG order: a failing test stops everything downstream of it
    yield from dbt.cli(["build"], context=context).stream()


@asset(deps=[northwind_models])
def published_marts() -> None:
    """Copy gold into Postgres, which is what Power BI and the AI tools connect to."""
    con = duckdb.connect("/data/northwind.duckdb")
    # Credentials come from the PG* environment, injected from the vault at start-up.
    con.execute("ATTACH 'dbname=marts host=marts.northwind.example' AS pg (TYPE postgres)")
    for table in GOLD_TABLES:
        # One transaction per table: readers see yesterday's table or today's, never half.
        con.execute("BEGIN")
        con.execute(f"DROP TABLE IF EXISTS pg.gold.{table}")
        con.execute(f"CREATE TABLE pg.gold.{table} AS SELECT * FROM gold.{table}")
        con.execute("COMMIT")
    con.close()


nightly = ScheduleDefinition(
    job=define_asset_job("nightly", selection="*"),
    cron_schedule="30 2 * * *",                 # after the agents' 02:00 push
    execution_timezone="Africa/Johannesburg",
)

defs = Definitions(
    assets=[northwind_models, published_marts],
    schedules=[nightly],
    resources={"dbt": DbtCliResource(project_dir=PROJECT)},
)

03

Version B, scale and freshness: CDC, Kafka, Iceberg and Trino

CoreVersion B
Difficulty

The story

Now change the constraints. An acquisition and cold-room temperature telemetry multiply the data tenfold, operations want stock and shipment dashboards fresh within five minutes, and finance, operations and commercial each want to build their own models. A nightly batch cannot deliver minutes, and one node cannot comfortably scan 2.5 TB. The shape becomes a log-based pipeline: SQL Server CDC, read by Debezium on Kafka Connect, into Kafka or Redpanda topics, committed continuously into Apache Iceberg tables on object storage, queried by Trino for ad-hoc and dbt work, with ClickHouse only for the few dashboards that need sub-second answers over hot data.

Iceberg is what makes this a lakehouse rather than a pile of files: atomic snapshot commits, schema evolution, hidden partitioning, time travel, and a REST catalog that lets Trino, Spark and ClickHouse read the same tables. Bronze holds the append-only change stream; a MERGE folds it into silver current state, guarded by the source LSN so a replayed window is harmless; gold is dbt models, one namespace per team. The closed Botswana network does not change: its agent still pushes (05), and the ingest API now produces to the same topics the connectors write.

Trade-off: freshness and scale are bought with operating burden. You now run Kafka, Connect, a catalog, Trino and perhaps ClickHouse, and you own compaction, snapshot expiry, connector restarts after schema changes, and consumer lag. That needs a platform team of three or more. Without one, Version B decays into a system that looks fresh on the slides and has stale corners nobody notices, which is worse than an honest daily batch.

Use when
  • Terabytes and growing, with many consumers
  • Minutes-level freshness that someone has funded
  • Several teams needing isolation over shared tables
  • You want open tables as a hedge against any one engine
Avoid
  • Two engineers and daily needs: a cluster for a spreadsheet's worth of data
  • Sources where you cannot enable CDC (use the agent)
  • ClickHouse as the system of record

-- 2. In Trino: fold the append-only change stream (bronze) into current state (silver).
--    Guarded by the source LSN, so replaying a window of changes is harmless.
merge into iceberg.silver.gl_entry as t
using (
    select *
    from (
        select *,
               row_number() over (
                   partition by entity_code, entry_no
                   order by source_lsn desc) as rn
        from iceberg.bronze.erp_gl_entry_changes
        where ingested_at >= timestamp '2026-10-08 06:00:00'   -- the job's watermark
    ) as changes
    where rn = 1
) as s
on t.entity_code = s.entity_code and t.entry_no = s.entry_no
when matched and s.source_lsn > t.source_lsn and s.op = 'd' then delete
when matched and s.source_lsn > t.source_lsn then update set
    account_no = s.account_no,
    amount_lcy = s.amount_lcy,
    posting_date = s.posting_date,
    source_lsn = s.source_lsn
when not matched and s.op <> 'd' then insert
    (entity_code, entry_no, account_no, amount_lcy, posting_date, source_lsn)
    values (s.entity_code, s.entry_no, s.account_no, s.amount_lcy, s.posting_date, s.source_lsn);

-- 3. Housekeeping you now own: small files from frequent commits, and old snapshots.

# freshness.py: how old is the newest committed data, per table? Runs every minute.
# Plain Python worker: it reads the catalog and emits metrics; it serves no requests.
import time

from pyiceberg.catalog import load_catalog

catalog = load_catalog(
    "northwind",
    **{
        "type": "rest",
        "uri": "https://catalog.northwind.example",
        "warehouse": "lakehouse",
        # auth: OAuth client credentials, read from the environment
    },
)

SLO_SECONDS = {
    "silver.gl_entry": 10 * 60,
    "silver.stock_movement": 5 * 60,
    "silver.shipment": 5 * 60,
}


def lag_seconds(identifier: str) -> float:
    table = catalog.load_table(identifier)
    snapshot = table.current_snapshot()
    if snapshot is None:
        return float("inf")                 # never committed: maximally stale
    # Commit time is a proxy. The honest lag is now minus the newest *source*
    # timestamp in the data; track both, alert on the second.
    return time.time() - snapshot.timestamp_ms / 1000


def breaches() -> list[str]:
    found = []
    for identifier, slo in SLO_SECONDS.items():
        lag = lag_seconds(identifier)
        if lag > slo:
            found.append(f"{identifier}: {lag / 60:.0f} min old (SLO {slo // 60} min)")
    return found


if __name__ == "__main__":
    for line in breaches():
        print("FRESHNESS BREACH", line)     # in production: a gauge, alerted on burn rate

04

Version C, managed: Microsoft Fabric and OneLake

CoreVersion C
Difficulty

The story

Third constraint set: a small team, an estate that is already Entra ID, Microsoft 365 and Power BI, and leadership that would rather buy than build. Microsoft Fabric puts the pieces under one capacity: OneLake as the single lake with Delta Parquet underneath, Lakehouses and Warehouses over it, Data Factory pipelines and mirroring for ingestion, notebooks for Spark, and Power BI semantic models in Direct Lake mode, which read the Delta tables without an import copy. The reachable ERPs come in through pipelines and the on-premises data gateway. For Botswana the push agent lands files in OneLake and a notebook folds them into bronze; the contract from 05 is unchanged.

What you gain: no servers to patch, one bill, Entra sign-in and permissions everywhere, lineage and sensitivity labels through Purview, fast Power BI over Direct Lake, and Copilot over the same semantic model. What you lose: control of the engine and its settings, a release cadence you do not set, and isolation. Pipelines, Spark, SQL and Power BI all draw on one pool of capacity units, so a runaway notebook can throttle the finance director's dashboard on the morning of the board pack. Size the capacity for the month-end peak, or split heavy engineering work onto its own capacity.

Trade-off: the lock-in is real but uneven. The data stays open: Delta Parquet in OneLake is readable through ADLS-compatible APIs and by any Delta reader. The work does not: pipelines, Dataflows, semantic models and capacity sizing are Fabric's. Keep the transformation logic in dbt (the dbt-fabric adapter) or plain SQL in Git, and the exit cost stays a migration of plumbing, not of business logic. One practical trap: Direct Lake reads Delta tables, not views, so materialise gold as tables or the model quietly falls back to DirectQuery.

Use when
  • Microsoft estate, with Power BI as the BI tool
  • One to three engineers and no appetite for running servers
  • Lineage, labels and access governance wanted out of the box
Avoid
  • Workloads that must run outside Microsoft's cloud
  • Heavy, spiky Spark beside latency-sensitive dashboards on one small capacity
  • Expecting the capacity bill to stay flat without anyone watching it

Getting data out of a network that allows no inbound connections

CriticalIngestion
Difficulty

The story

The Botswana ERP's hosting provider allows no inbound connections and no VPN. That rules out every pull-based option: a connector dialling in, a replica, a cloud service polling the database. What is allowed is one outbound HTTPS rule. So invert the direction. A small push agent runs inside the network, reads changes locally and pushes them out, the same shape as a monitoring agent or a card terminal: the side behind the wall starts every connection. It authenticates with a client certificate of its own, so a compromised box can only write its own entity's batches, and it never listens on a port, not even "just for health checks".

The agent uses SQL Server change tracking rather than CDC: no SQL Agent jobs, little overhead, and a version number per change that is exactly the watermark you need. Each run reads CHANGETABLE from the last acknowledged version to the current one inside a snapshot transaction, writes a Parquet batch, and PUTs it to the ingest API under a deterministic batch id (entity, table, from-version, to-version). The API verifies the checksum and writes put-if-absent. The watermark advances only after a 2xx. Lose the response and the agent resends the same range: same id, same object, no-op. Crash and rerun, and the next range overlaps the last: harmless, because silver keeps the latest version per key. Gaps are the only real danger, and the watermark rule prevents them.

Edge case: the agent is offline longer than change-tracking retention. CHANGE_TRACKING_MIN_VALID_VERSION is now above the watermark and the incremental changes are gone. The agent must detect it, take a full snapshot of the table, and flag the batch so the platform replaces that table rather than appending. Set retention (seven days here) against the longest outage you will tolerate, and alert on agent silence long before it runs out.

Use when
  • Sources behind firewalls you do not control
  • Third-party hosted systems and small remote sites
  • You need idempotent, auditable landing with checksums
Avoid
  • Agents holding storage account keys
  • Advancing the watermark before the acknowledgement
  • Agents that take commands from the cloud: an inbound path by another name
Connects to Idempotency, Idempotency keys, Change Data Capture, mTLS & service identity
Docs: SQL Server change tracking · FastAPI

set transaction isolation level snapshot;   -- changes and @now_version from one moment
begin transaction;

declare @last_version bigint = 418213;      -- from the agent's watermark file
declare @now_version  bigint = change_tracking_current_version();
declare @open_from    date   = '2026-09-01';  -- first open period; closed ones are certified

if @last_version < change_tracking_min_valid_version(object_id('dbo.GLEntry'))
    throw 50001, 'Watermark older than retention: full re-snapshot required.', 1;

# agent.py: runs inside the BW network as a Windows service. Plain Python worker on
# purpose: it must never listen on a port, so it is not a web app. It only calls out.
import hashlib
import io
import json
import pathlib
import time
from typing import Annotated

import httpx
import pyarrow.parquet as pq

STATE = pathlib.Path("C:/ProgramData/NorthwindAgent/watermarks.json")
ENDPOINT = "https://ingest.northwind.example/v1/batches"
TABLES = ("GLEntry", "SalesInvoice", "Customer", "StockMovement")


def push_once(table: str, client: httpx.Client) -> None:
    marks = json.loads(STATE.read_text())
    last = marks[table]
    rows, now_version = read_changes(table, last)       # the CHANGETABLE query, in a snapshot
    if rows.num_rows == 0:
        return
    batch_id = f"NCC-BW.{table}.{last}-{now_version}"   # deterministic: same range, same id
    buf = io.BytesIO()
    pq.write_table(rows, buf, compression="zstd")
    body = buf.getvalue()
    resp = client.put(
        f"{ENDPOINT}/{batch_id}",
        content=body,
        headers={"Content-SHA256": hashlib.sha256(body).hexdigest()},
    )
    resp.raise_for_status()                             # 201 landed, or 200 already had it
    marks[table] = now_version                          # advance ONLY after the ack
    STATE.write_text(json.dumps(marks))


def run(cert: tuple[str, str]) -> None:
    with httpx.Client(cert=cert, timeout=60) as client:   # mTLS: the cert is the identity
        while True:
            for table in TABLES:
                try:
                    push_once(table, client)
                except httpx.HTTPError as exc:
                    log_and_back_off(table, exc)          # watermark unchanged: next run resends
            time.sleep(900)


# ingest.py: the receiving side, in the platform. An HTTP service, so FastAPI.
from fastapi import FastAPI, Header, HTTPException, Request, Response

app = FastAPI()


@app.put("/v1/batches/{batch_id}", status_code=201)
async def land(batch_id: str, request: Request, response: Response,
               content_sha256: Annotated[str, Header(alias="Content-SHA256")]):
    entity = entity_from_client_cert(request)           # set by the mTLS-terminating proxy
    if not batch_id.startswith(f"{entity}."):
        raise HTTPException(403, "an agent may only write its own entity")
    body = await request.body()
    if hashlib.sha256(body).hexdigest() != content_sha256:
        raise HTTPException(422, "checksum mismatch: resend")
    blob = landing.get_blob_client(blob_path(batch_id))  # landing/erp/<table>/entity_code=<e>/<id>.parquet
    if await blob.exists():
        response.status_code = 200                       # a replay: already landed, no-op
        return {"batch_id": batch_id, "status": "duplicate"}
    await blob.upload_blob(body, overwrite=False)       # put-if-absent closes the race
    return {"batch_id": batch_id, "status": "landed"}

Proving the numbers: reconciliation, contracts and health

CriticalOps
Difficulty

The story

Finance will judge the whole platform on one test: does the pack match the ERP? So make the platform prove it on every load instead of waiting for someone to notice. The agent computes control totals at the source, in the same snapshot transaction as the batch: per entity, period and account, the sum of functional-currency amounts and the line count. The platform recomputes the same aggregates from gold, and a reconciliation test compares the two exactly, in decimal, in the currency the ERP books in. Every difference names the entity, period and account, which is precisely the line an accountant needs to investigate.

Data contracts catch the other class of breakage: an ERP upgrade renames a column, or a WMS starts sending quantities in cases instead of units. dbt model contracts fail the build when a gold model's columns or types drift; tests check keys, accepted values and relationships; source freshness measures the age of the newest landed row per entity. Upstream, the agent refuses to ship a table whose shape changed without a schema version bump, so the break shows up at the edge with a clear message instead of as a wrong total three layers later.

Health is an outcome, not an exit code. A pipeline that ran green and published wrong numbers is the worst failure there is, because people act on it. Define health per entity from three signals (fresh within its SLO, reconciled with zero differences, contracts held), alert on those, and stamp the status and data timestamp on every report page. Amber, late but right, is shown as such; red blocks the month-end pack. Route alerts by meaning: differences go to that entity's finance team, staleness and broken contracts to the platform on-call.

Use when
  • Every load, not only at month-end
  • Exact comparison in functional currency
  • Status visible to the people reading the numbers
Avoid
  • Alerting only on job failure
  • Tolerances that quietly absorb real errors
  • Hand-adjusting the platform number until it matches

# health.py: health is computed from outcomes (fresh? reconciled? contract held?),
# not from whether last night's job exited 0. Plain Python checks run by Dagster.
from dataclasses import dataclass
from datetime import datetime, timedelta, timezone

from dagster import AssetCheckResult, AssetCheckSeverity, asset_check


@dataclass
class EntityHealth:
    entity: str
    newest_source_row: datetime
    recon_differences: int
    failed_tests: int

    def status(self, max_age: timedelta) -> str:
        if self.recon_differences or self.failed_tests:
            return "red"        # wrong numbers are worse than late numbers
        if datetime.now(timezone.utc) - self.newest_source_row > max_age:
            return "amber"      # right but stale: say so on every report page
        return "green"


@asset_check(asset="fct_gl_monthly", blocking=True)
def gl_reconciles_to_erp() -> AssetCheckResult:
    # The dbt test stored its failures; this turns them into a check that blocks publishing.
    rows = warehouse.query("select entity_code, period_key, account_code, difference "
                           "from audit.gl_recon_differences")
    by_entity: dict[str, int] = {}
    for r in rows:
        by_entity[r.entity_code] = by_entity.get(r.entity_code, 0) + 1
    return AssetCheckResult(
        passed=not rows,
        severity=AssetCheckSeverity.ERROR,
        metadata={"differences_by_entity": by_entity},
    )


def can_publish_pack(entities: list[EntityHealth]) -> bool:
    # The month-end pack goes out only when every entity in it is green.
    return all(e.status(max_age=timedelta(hours=26)) == "green" for e in entities)


def alert_routes(h: EntityHealth) -> list[str]:
    # Route by meaning: finance owns differences, the platform team owns staleness.
    routes = []
    if h.recon_differences:
        routes.append(f"finance-{h.entity.lower()}")
    if h.failed_tests or h.status(timedelta(hours=26)) == "amber":
        routes.append("data-platform-oncall")
    return routes

Security and governance: identity, RLS for BI and the AI assistant, POPIA

SecurityGovernance
Difficulty

The story

Identity first. Every person signs in with Entra ID, everywhere: Power BI, the SQL endpoint, Trino over OAuth, and the assistant. Every workload has its own identity with one job: the ingest API writes landing (agents have no storage role at all), the transform identity reads landing and writes the lake, the BI layer reads gold. No person holds write access to production tables; changes arrive through dbt in Git and a pipeline. Credentials are managed identities and certificates, never passwords in config files.

Row-level security is where most designs break, because there are several doors. Power BI enforces RLS with roles filtered on USERPRINCIPALNAME(); the database enforces it with a security policy on the caller's login. Both must read one entitlement table (user, entity, cost centre), owned by finance and audited. Watch import mode: a dataset refreshed by a service account bypasses database RLS, so the semantic model's own roles must do the filtering. The AI assistant is the newest door. It calls curated, parameterised tools with an on-behalf-of token for the asking user, so the database applies that user's rows. An assistant running as a service account that sees every entity turns any question into a cross-entity leak, and prompt injection hidden in the data makes that worse. Log every tool call with the user, the arguments and the row count.

PII and POPIA. Classify columns in the contract: customer contacts, driver and employee details. Keep raw PII only in a restricted bronze area with short retention, hash or drop it in silver, and keep it out of gold and out of the assistant's tools unless a stated purpose needs it. POPIA asks for a lawful purpose, minimality, security safeguards and notification of compromises, and it restricts sending personal information outside South Africa (section 72). That matters when you choose the cloud region and move Namibian and Botswana data, which bring their own jurisdictions too: get the data-residency decision signed off by the information officer instead of letting a default region make it.

Use when
  • One entitlement table, enforced at every door
  • On-behalf-of tokens for anything acting for a user
  • PII classified in the contract, not discovered later
Avoid
  • A shared "powerbi" or "assistant" login
  • Letting the model write free SQL against gold
  • PII in gold "because a dashboard might need it"
Connects to Least privilege & IAM, Secrets management, RBAC vs ABAC, Audit logging

Choosing between them: trade-offs and the triggers to move

DecisionArchitecture
Difficulty

The story

Score the three on the axes that actually decide: cost, freshness, operating effort, lock-in, and how each one fails. A is the cheapest and simplest; it fails loudly (the node dies or the window overruns) and recovers by rerunning. B is the freshest and scales furthest, costs the most in people, and fails quietly: consumer lag, an uncompacted table, one connector stuck after a schema change while the dashboards look fine. C costs a predictable capacity fee, needs the fewest engineers, and fails by throttling: everything on the capacity slows down at once, usually at month-end.

For Northwind today the answer is A. The numbers fit one node with room to spare, daily plus hourly is the real freshness need, and two engineers can run it well. The triggers to move are concrete and measurable: data scanned past about a terabyte, or the nightly run nearing its window; operations committing to (and funding) minutes-level freshness; a third team writing models. If those fire and there is a platform team, move to B. If they fire and there is not, move to C, which a Microsoft estate makes the natural purchase. Saying the trigger out loud is what turns an opinion into a design.

Design for the move, not only the version. The seams that make migration cheap are the same in every version: open files (Parquet, Delta, Iceberg) as the durable copy, business logic in dbt models that run on DuckDB, Trino and Fabric, one entitlement table, and reconciliation tests that travel with the models. Get those right and moving from A to B or C is a re-platform of plumbing over a quarter, with the same tests proving the new system matches the old one before anyone switches over.

Say in the interview
  • The constraint that picks the design
  • The trigger that would change your answer
  • The seam that makes changing it cheap
Avoid
  • Choosing by fashion, or by what looks good on a CV
  • Comparing licence cost and ignoring operating effort
  • A design with no exit
Connects to Version A, Version B, Version C, Polyglot persistence

# choose.py: the triggers, written down, so the decision is argued once
# and revisited on evidence rather than on fashion.
from dataclasses import dataclass


@dataclass
class Situation:
    scanned_tb: float               # data the nightly and ad-hoc queries scan, not total stored
    freshness_minutes: int          # the tightest freshness someone has agreed to fund
    teams_writing_models: int
    platform_engineers: int
    microsoft_estate: bool          # Entra ID, Microsoft 365, Power BI already in place
    must_run_outside_microsoft: bool


def choose(s: Situation) -> tuple[str, list[str]]:
    triggers = []
    if s.scanned_tb > 1:
        triggers.append("past ~1 TB scanned, one node stops being comfortable")
    if s.freshness_minutes < 30:
        triggers.append("minutes-fresh needs CDC and a log, not a scheduled batch")
    if s.teams_writing_models >= 3:
        triggers.append("several teams need namespaces, a catalog and isolation")

    if not triggers:
        return "A: DuckDB + dbt", ["small, daily, one team: the cheapest design that is correct"]
    if s.platform_engineers >= 3 or s.must_run_outside_microsoft:
        return "B: CDC + Iceberg + Trino", triggers
    if s.microsoft_estate:
        return "C: Fabric", triggers + ["no team to run B, and the estate is already Microsoft"]
    return "B, staffed first", triggers + ["hire or buy the operating capacity before building"]


if __name__ == "__main__":

    grown = Situation(2.5, 5, 4, 2, True, False)
    print(choose(today))    # ('A: DuckDB + dbt', [...])
    print(choose(grown))    # ('C: Fabric', [...]): B's triggers, without B's team
